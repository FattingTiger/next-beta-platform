# Android 内测分发平台服务端技术选型记录 V0.1

> 日期：2026-08-29  
> 状态：开发基线建议  
> 范围：服务端、管理后台构建链、APK 校验、数据库与测试基础设施  
> 依据：`docs/需求分析-V0.2-内测平台.md`

## 1. 结论

首版采用以下组合：

| 层次 | 选择 | 版本策略 |
| --- | --- | --- |
| 服务端语言 | Python | `3.12.x`，项目约束为 `>=3.12,<3.13` |
| Web API | FastAPI + Pydantic | 由 `uv.lock` 固定精确版本 |
| 数据访问 | SQLAlchemy 2 + psycopg 3 | 同上 |
| 数据库迁移 | Alembic | 迁移文件进入版本控制，发布时只执行迁移 |
| 生产数据库 | PostgreSQL 17 | 使用当前 17 系列补丁版；发布镜像固定 digest |
| 密码哈希 | Argon2id（`argon2-cffi`） | 参数写入配置并支持以后重哈希 |
| 管理后台 | React 19 + TypeScript + Vite | Node 24 LTS；`package-lock.json` + `npm ci` |
| 文件传输 | Nginx 内部受控路径 | API 鉴权后用 `X-Accel-Redirect` 交给 Nginx 传输 |
| APK 元数据 | Android SDK Build Tools 的 AAPT2 | 固定 Build Tools `36.0.0` |
| APK 签名 | Android SDK Build Tools 的 `apksigner` | `verify --verbose --print-certs`，以退出码和证书 SHA-256 为准 |
| 部署编排 | Docker Compose | 开发、测试、生产使用分层 Compose 文件 |
| 自动测试 | pytest、Testcontainers、Vitest、Playwright、k6 | PostgreSQL 容器测试是发布门禁 |

这个组合适合当前不超过 100 名用户的规模，也保留了后续扩展对象存储、CI 上传接口和多管理员权限的空间。首版不引入 Redis、Celery、MinIO、Kubernetes 或微服务；这些组件现在只会增加部署、备份和故障面。

## 2. 选择理由

### 2.1 为什么服务端选择 Python/FastAPI

- 业务主体是鉴权、关系数据、上传校验、图片处理、审计和状态流转，FastAPI、SQLAlchemy、Pillow 与 pytest 能用较少的框架胶水覆盖这些工作。
- OpenAPI 是 FastAPI 的原生输出，可作为管理后台与 Android 客户端的共同接口契约。
- APK 校验最终调用 Android 官方工具，选择 Python 或 Node 都不会消除这个外部工具边界。Python 在受控子进程、流式哈希、图片缩略图和测试夹具方面更直接。
- 当前本机通过 `uv` 可以解析 Python 3.12 依赖并生成带哈希的锁定结果；代表性依赖也完成了真实安装与导入验证。

### 2.2 为什么没有选择 Node 作为服务端

Node/Fastify 同样可行，本机包安装也已经验证。不过本项目仍需要单独携带 Android Build Tools/JRE，Node 并不能降低 APK 校验部分的复杂度。保留 Node 24 LTS 仅用于管理后台构建，可减少后端异步风格、ORM 方言和二进制图片处理上的额外决策。

本机 Node 26 属于 Current 版本，不作为生产基线。Node 官方建议生产应用使用 Active LTS 或 Maintenance LTS，因此管理后台构建固定在 Node 24 LTS。

### 2.3 为什么没有选择 JVM 服务端

JVM 可以直接使用 Android `apksig` 库，技术上很稳健；但当前业务没有必须依赖 JVM 的能力，服务端整体开发和容器体积会更重。本机虽有 Android Studio 自带 JBR，但命令行没有独立 JDK 配置。首版采用官方 CLI 工具，仍可获得 Android 平台一致的签名验证语义；如果未来需要支持签名密钥轮换谱系或复杂 APK 分析，可再将 APK 检查器替换为小型 JVM 组件，业务 API 无需改变。

## 3. 服务端运行结构

建议在单台服务器中部署四个容器：

1. **gateway**：Nginx，终止 HTTPS、托管管理后台静态文件、执行上传大小限制和登录限流，并传输受保护 APK/图片。
2. **api**：FastAPI，负责认证、授权、业务规则、管理后台 API、Android API 和审计。
3. **worker**：与 API 使用同一应用镜像，负责 APK 检查、图片缩略图和后续可恢复的异步任务；使用 PostgreSQL 行锁领取任务，不额外引入消息队列。
4. **db**：PostgreSQL 17，仅绑定 Compose 私有网络，不向公网发布端口。

API 和 worker 共享受控文件卷，但权限不同：

- API 可写 `quarantine/`，不能直接把上传内容标记为已发布。
- worker 从 `quarantine/` 读取，校验通过后原子移动到不可覆盖的 `objects/`。
- gateway 对 `objects/` 只读，并把目录配置为 Nginx `internal`；外部不能直接枚举或访问真实存储键。

下载流程为：客户端请求下载 → API 再次检查账号、测试组、应用和版本状态 → 写入“下载开始”事件 → API 返回内部重定向头 → Nginx 支持 Range/断点续传 → 客户端核对 SHA-256 后调用幂等完成接口 → 服务端记录“下载完成”。这不会把下载完成误记为安装成功。

## 5. 身份认证与权限基线

### 5.1 会话

首版使用服务端会话，而不是不可立即撤销的长时 JWT：

- 登录成功后生成至少 256 bit 随机令牌，数据库只保存令牌哈希。
- 管理后台使用 `HttpOnly + Secure + SameSite` Cookie，并启用 CSRF 防护。
- Android 使用 Bearer 会话令牌，客户端保存到 Android 安全存储。
- 每次请求通过会话关联用户并检查账号启用状态；禁用账号或撤销会话可以立即生效。
- 会话设置绝对过期时间和空闲过期时间，密码重置后撤销原会话。

### 5.2 授权

“列表中不显示”不构成授权。以下每一个接口都要在服务端重新判断测试组并集：

- 应用详情、版本信息和产品截图；
- APK 下载和下载完成回执；
- 应用 Bug 列表、Bug 详情和 Bug 截图；
- 新建 Bug 时提交的应用与版本组合。

管理员动作采用单独的管理员依赖/策略，不把客户端传入的角色字段当作权限依据。

## 6. APK 上传与检查决策

### 6.1 推荐：Android 官方工具作为发布门禁

上传检查按以下顺序执行：

1. 流式写入随机命名的隔离文件，同时计算 SHA-256；限制请求大小、文件数量和处理时间。
2. 校验 APK/ZIP 结构、实际文件类型和单 APK 边界，拒绝 AAB、APKS 与 split APK。
3. 使用 AAPT2 `dump badging` 读取包名、`versionCode`、`versionName`、`minSdkVersion`、`targetSdkVersion` 和应用标签。
4. 使用 `apksigner verify --verbose --print-certs` 验证 APK 是否能在其声明支持的 Android 平台上通过签名验证，并记录签名方案、签名者数量和证书 SHA-256。
5. 对已有应用检查包名一致、`versionCode` 严格递增、签名证书连续；首版不自动接受签名轮换谱系，出现轮换必须走显式迁移流程。
6. 校验通过后原子移动到以随机存储键寻址的不可变对象目录，数据库记录文件 SHA-256、大小、证书摘要和工具版本。
7. 已发布对象永不原地覆盖；内容变化必须产生新的版本记录和存储对象。

每个工具子进程必须使用非 root 用户、固定工作目录、参数数组而非拼接 shell、超时、输出上限和并发上限。平台只验证签名，不接收或保存业务应用的签名私钥。

Android 官方说明 `apksigner` 用来确认 APK 签名能否在 APK 支持的各 Android 版本上成功验证，并支持 `--print-certs` 输出签名证书信息；AAPT2 的 `dump badging` 用于从 APK manifest 提取基础元数据。

### 6.2 备选项

| 方案 | 优点 | 风险 | 决定 |
| --- | --- | --- | --- |
| AAPT2 + `apksigner` CLI | Android 官方语义；覆盖 v1/v2/v3/v3.1/v4；真实验证证书 | 需要固定 JRE 和 Build Tools；需封装输出解析 | **采用** |
| Java `apksig` 库 | 可用结构化 API；签名能力完整 | 引入 JVM 服务或辅助程序及独立构建链 | 以后复杂签名场景再考虑 |
| Androguard | Python 内直接读取 manifest、DEX 和证书 | 发布门禁语义未必与目标 Android 平台完全一致；依赖面更大 | 仅可作诊断，不作最终签名判定 |
| `apkutils2` 等轻量解析库 | 接入快 | 维护状态与签名覆盖难作为安装有效性的依据 | 不采用为发布门禁 |

### 6.3 工具镜像可重复性

API/worker 镜像构建时固定：

- Python 3.12 基础镜像的完整 digest；
- JRE 21 发行版、版本和镜像 digest；
- Android Command-line Tools 下载版本与 SHA-256；
- Android SDK Build Tools `36.0.0`；
- `uv.lock`，构建使用 `uv sync --locked`；
- 运行时非 root 用户和只读根文件系统。

为避免 CLI 文本格式变化造成误判，`apk/` 适配器需要保存多组已签名、未签名、篡改、错包名、同版本号和不同签名的黄金 APK 夹具，并对解析结构做回归测试。

## 7. PostgreSQL 与 SQLite 测试策略

### 7.1 生产与发布门禁只认 PostgreSQL

生产选择 PostgreSQL 17。PostgreSQL 官方支持每个大版本五年；截至本记录日期，17 系列当前补丁版为 17.11，支持期到 2029 年 11 月。部署跟随 17 系列安全补丁，不跨大版本自动升级。

以下内容必须在真实 PostgreSQL 容器中测试：

- Alembic 从空库升级到最新版本，以及从上一发布版本升级；
- 唯一约束、外键、部分索引、时间和 JSON 行为；
- 发布新版本、领取 worker 任务和 Bug 状态迁移中的事务/行锁；
- 手机号唯一、一个应用一个当前版本、幂等下载完成等并发竞争；
- PostgreSQL 备份与附件清单的恢复演练。

Testcontainers/Compose 使用与生产相同大版本的 PostgreSQL 镜像。测试数据库只通过 Alembic 建立，不能用 ORM `create_all()` 代替迁移验证。

### 7.2 SQLite 的有限用途

SQLite 只用于：

- 不涉及数据库语义的 domain/service 快速测试；
- 非关键查询的开发期烟雾测试；
- 必须显式打开 `PRAGMA foreign_keys=ON` 的少量 repository 试验。

SQLite 不能用于证明生产数据库正确。本机实测 SQLite 3.54.0 的内存数据库默认 `PRAGMA foreign_keys=0`，插入不存在父记录的子记录仍然成功；这与生产期望直接冲突。它在锁、并发、类型、约束和 JSON 细节上也不等同于 PostgreSQL。

推荐测试分层：

| 层级 | 数据库 | 运行时机 | 是否为发布门禁 |
| --- | --- | --- | --- |
| 领域单元测试 | 无数据库；必要时 fake repository | 每次保存/提交 | 是 |
| 轻量烟雾测试 | SQLite 内存库 | 本地快速反馈 | 否 |
| repository/迁移/并发集成测试 | PostgreSQL 17 Testcontainer | 每个合并请求和发版 | 是 |
| API 端到端 | 完整 Compose 栈 | 每个合并请求关键路径、发版全量 | 是 |
| 备份恢复与压力 | 独立测试栈 | 候选版本三轮验收 | 是 |

## 8. 三轮服务端测试建议

这三轮使用独立测试报告与全新数据库/文件卷，上一轮通过不能替代下一轮。

### 第一轮：功能与契约

- 用户、测试组、应用授权矩阵；禁用用户的即时失效。
- APK 正常上传及未签名、篡改、包名变化、签名变化、版本未递增的拒绝路径。
- 应用发布/停止下载/下架，Bug 四状态及非法状态迁移。
- 下载开始/完成幂等记录，历史数据保留。
- OpenAPI 兼容检查、迁移从空库和上一版本升级。

### 第二轮：管理 UI、权限与故障恢复

- Playwright 覆盖管理员登录、用户/组/应用/版本/Bug/下载记录完整流程。
- 键盘、焦点、错误文案、上传进度、刷新恢复、窄桌面布局和关键颜色对比度。
- 越权对象 ID、失效下载地址、CSRF、登录限流、非法 MIME、超限上传和路径穿越。
- worker 中止后任务重新领取、API 重启、数据库短暂断开、磁盘空间不足等故障注入。

### 第三轮：压力、恢复与发布候选

- k6 模拟 100 个账户，分别测试登录/列表/Bug 控制面和 APK Range 下载数据面。
- 对登录、授权查询、Bug 列表、下载授权分别记录 p50/p95/p99、错误率、CPU、内存和数据库连接数。
- 并发发布与下载时验证版本不可覆盖、授权即时生效、下载记录不丢失。
- 完成数据库 + 文件对象联合备份，并在全新目录恢复后跑验收场景。
- 使用最终生产镜像和 Compose 配置测试，不接受开发服务器或本机依赖替代。

具体性能阈值应在首个可运行版本中用基线压测确定；建议先以普通 API p95 小于 500 ms、错误率低于 0.1% 为候选门槛，APK 吞吐单独按服务器带宽和磁盘能力验收，不能把大文件传输延迟混入普通 API 指标。

## 9. 构建与发布可重复性

- Python 使用 `pyproject.toml` 声明范围，`uv.lock` 固定解析结果；CI 执行 `uv lock --check` 和 `uv sync --locked`。
- 管理后台提交 `package-lock.json`，CI 使用 Node 24 LTS + `npm ci`，不用本机 Node 26 的 Current 环境作为发版依据。
- Dockerfile 不使用 `latest`；基础镜像、PostgreSQL、Nginx 和构建工具在发布清单中固定完整 digest。
- 依赖升级由独立提交完成，带单元、集成、E2E 与依赖漏洞扫描结果；构建时不隐式升级锁文件。
- 生成并保存 OpenAPI、数据库迁移版本、应用 Git commit、镜像 digest、APK 工具版本和 SBOM。
- 开发 `compose.yaml` 与 `compose.production.yaml` 分离。生产文件取消源代码 bind mount、限制容器权限、设置健康检查、资源上限、日志轮转和重启策略。
- 所有密钥、数据库密码、Cookie 密钥和部署凭据从项目文件外注入；示例环境文件只保留字段名和安全生成说明。

`uv` 官方文档说明锁文件记录精确解析版本并应进入版本控制，`--locked` 可在锁文件过期时直接失败；Docker 官方也建议用额外的生产 Compose 文件覆盖端口、环境变量、重启策略等生产差异。

## 10. 服务器部署隔离要求

本记录没有连接任何远程服务器，也没有启动或修改本机/远程系统服务。

以后部署前必须先执行只读盘点并形成端口与目录清单：监听端口、现有容器、systemd 服务、反向代理、路由、防火墙规则、Docker 网络、磁盘和备份目录。现有 VPN 服务及其配置、端口、进程、路由、防火墙规则和运行目录全部列为禁止改动项。

只有确认无冲突后才能：

- 创建独立的低权限部署账户和独立应用目录；
- 使用唯一 Compose project name、独立 bridge network、命名卷和日志目录；
- 只发布经过确认的端口，数据库和 worker 不映射宿主机公网端口；
- 不执行全局 Docker 清理、不改默认路由、不刷新防火墙、不复用现有服务目录；
- 部署前后分别记录现有 VPN 的进程、监听端口和健康状态，出现变化立即回滚应用部署。

HTTPS 端口和域名方案必须等只读盘点后决定，不能先假设 80/443 可用。
