# Android 内测分发平台：服务端架构与威胁模型

> 状态：实施基线  
> 日期：2026-08-29  
> 依据：需求分析 V0.2 与 PRODUCT.md  
> 范围：服务端、管理后台所需 API、数据库、APK/图片存储、部署、备份恢复与安全边界  
> 不包含：Android 客户端实现、管理后台视觉设计、恶意代码扫描服务、静默安装与 MDM

## 1. 结论

首版采用以下组合是合适的：

| 层次 | 选择 | 结论 |
| --- | --- | --- |
| API 与业务服务 | FastAPI | 适合。接口类型明确、OpenAPI 完整、测试成本低，足以支撑 100 人以内的公网内测平台 |
| 关系数据库 | PostgreSQL | 必选。发布、权限、Bug 状态和审计需要约束、行锁与事务，SQLite 不适合作为生产主库 |
| APK 与图片 | 服务器本地不可公开文件系统 | 适合首版。由 Nginx 内部文件位置受控发送，业务进程不承载 APK 长连接 |
| 异步任务 | PostgreSQL 任务表 + 独立 Worker | 首版不引入 Redis/Celery；APK 解析和图片处理必须脱离 API 进程且任务可恢复 |
| 公网入口 | 独立 Nginx 应用网关或现有合规入口 | 必须 HTTPS。实际绑定端口要在目标服务器只读盘点后决定 |
| 部署形态 | 独立账户、目录、进程和端口 | 不与 sing-box 共享账户、目录、网络能力、配置或生命周期 |

本方案有意不在首版部署 MinIO。单机 MinIO 与本地文件系统位于同一块磁盘时，并不会消除单点故障，却会增加服务、端口、凭据和备份复杂度。代码层应保留 ObjectStore 接口，使以后迁移到 S3 兼容存储时不改变业务模型。

服务端不能把“用户少”理解为“风险小”。平台位于公网，并保存可安装 APK、手机号、Bug 描述和可能含敏感内容的截图。首版至少要做到：

1. 每次详情、Bug、图片和下载访问都由服务端重新授权。
2. 已发布 APK 内容寻址、不可覆盖，并由客户端校验 SHA-256。
3. APK 在隔离 Worker 中解析，不能把上传文件当作可信 ZIP。
4. 数据库发布事务、文件落盘状态和审计记录均可恢复、可对账。
5. 目标服务器上的 sing-box 被登记为受保护的共存服务，不允许因部署平台而被修改或重启。

## 2. 范围与设计假设

### 2.1 已确认范围

- 公网部署，启用用户不超过 100 人。
- 员工使用自有 Android 手机，无 MDM、无定制 ROM。
- 用户由管理员创建，绑定唯一手机号，不能自行注册。
- 首版采用手机号加密码；若后续改为短信验证码，仅替换认证入口，不改变授权模型。
- 只有管理员上传 APK 和维护应用资料。
- 用户可见应用取其所有启用测试组授权应用的并集。
- 一个应用只有一个当前发布版本，历史版本默认不可下载。
- 只支持单 APK，不支持 AAB、APKS 或 split APK。
- APK 必须已经签名，平台不托管任何应用签名私钥。
- 下载开始和客户端下载校验完成分开记录，不宣称安装成功。
- Bug 关联具体应用和版本，状态为待处理、处理中、待验证、已关闭。
- 不接入恶意代码扫描，不做双人审核、灰度、推送、强制升级和远程卸载。

### 2.2 安全默认值

仍待产品确认的事项采用更保守默认值：

- Bug 文本默认只对提交人和管理员可见；管理员可改为“同应用授权测试者可见”。
- Bug 截图默认只对提交人和管理员可见，即使 Bug 文本已对测试者公开。
- 用户失去应用授权后，不能继续查看该应用的详情、APK、公共 Bug 或历史截图；其历史数据仍由管理员保留。
- 临时密码首次登录后必须修改。
- 管理员高风险操作要求重新验证密码；管理员 TOTP 双因素认证列为公网正式使用前的强烈建议项。

## 3. 质量属性与建议指标

| 属性 | 首版目标 |
| --- | --- |
| 授权正确性 | 未授权用户在列表、详情、Bug、图片、下载五层均得到相同拒绝结果 |
| 普通 API 性能 | 20 个并发登录用户下，服务端 P95 不高于 500 ms，错误率低于 0.5% |
| 下载隔离 | 20 个并发 APK 下载不占用 FastAPI Worker 持续传输文件 |
| 可恢复性 | 建议 RPO 不高于 6 小时，RTO 不高于 4 小时 |
| 可用性 | 单机架构不承诺高可用；进程失败可自动拉起，磁盘或整机失败依靠异机备份恢复 |
| 文件完整性 | 所有 APK 上传、存储、下载均使用同一个 SHA-256 对账 |
| 审计 | 管理员关键写操作与业务变更在同一数据库事务内留痕 |
| 隔离 | 平台部署、启动、停止、回滚不修改或重启 sing-box |

这些是工程验收基线，后续可根据目标服务器 CPU、内存、磁盘和带宽压测结果调整。

### 4.1 信任边界

1. **公网边界**：Android 客户端和浏览器输入全部不可信。
2. **应用网关边界**：只处理 TLS、请求上限、限流、静态管理页面与内部文件发送。
3. **业务边界**：FastAPI 负责身份、授权、状态机、事务和生成受控文件响应。
4. **解析边界**：APK、PNG、JPEG 均视为攻击载荷，在低权限 Worker 中处理。
5. **数据边界**：PostgreSQL 不暴露公网；对象目录没有公开 URL。
6. **主机共存边界**：sing-box 不属于本平台，由独立变更边界保护。
7. **灾备边界**：同机副本不算备份，至少一份加密备份必须离开目标服务器。

## 5. 服务拆分

### 5.1 应用网关

职责：

- 终止 HTTPS 或接收上游可信入口转发。
- 只允许正式域名，拒绝任意 Host。
- 设置请求体上限、连接超时、登录 IP 限流和安全响应头。
- 将 API 请求转给仅监听回环地址或私有 Unix Socket 的 FastAPI。
- 使用 Nginx internal 文件位置处理 APK 与图片 Range 请求。
- 不记录 Authorization、Cookie、下载令牌或完整手机号。

APK 不通过 FastAPI StreamingResponse 长时间传输。FastAPI 完成授权和下载事件创建后返回 X-Accel-Redirect，由 Nginx 的内部位置直接发送文件。这样下载并发不会耗尽 API Worker。

### 5.2 FastAPI 服务

按领域拆分路由与服务，不按数据库表机械拆分：

- 认证与会话
- 用户与管理员
- 测试组与授权
- 应用与展示素材
- APK 上传、版本与发布
- 下载
- Bug 与回复
- 审计与查询
- 健康检查

API 进程只做短事务、权限查询和任务编排。APK 解析、图片解码、缩略图、备份和清理都不放进 FastAPI BackgroundTasks，因为进程退出后该类任务没有持久性保证。

生产依赖必须锁定精确版本并由自动化测试验证升级。FastAPI 官方也建议固定已验证版本，而不是部署时自动获取最新版本。

### 5.3 PostgreSQL

PostgreSQL 同时承担：

- 强业务约束和关系完整性。
- 发布与 Bug 状态变更事务。
- 并发发布行锁。
- 持久任务队列和事务 Outbox。
- 不可物理删除的审计与历史数据。

首版不需要 Redis。登录限流由网关的 IP 维度限流与 PostgreSQL 的账号维度锁定共同实现；任务 Worker 使用任务表领取作业。

建议使用 SQLAlchemy 2.x 与 Alembic，依赖锁定到经过测试的精确版本。PostgreSQL Row-Level Security 不作为首版主要授权机制：组授权、Bug 可见性和文件引用跨越多张表，在连接池中注入请求身份会显著增加配置错误风险。首版以中央授权服务、受限 Repository 和完整负向权限测试作为主防线，数据库负责关系不变量与最小账户权限。若以后拆成多服务或开放分析查询，可在独立安全评审后增加 RLS 作为纵深防御。

### 5.4 任务 Worker

独立进程至少处理：

- APK 校验与元数据解析。
- 图片格式验证、解码、EXIF 清理、重编码和缩略图。
- 过期临时上传清理。
- 文件与数据库对账。
- Outbox 事件投递或内部派生统计。

Worker 从任务表用行锁领取任务。多 Worker 时可用 FOR UPDATE SKIP LOCKED，任务需要租约、超时回收、最大重试次数和幂等处理。

Worker 编排进程需要数据库与 staging 权限，但真正调用 apksigner、aapt2 和图片解码器的 Parser 子进程使用更低权限账户，只得到单个输入文件和临时输出目录，不获得数据库连接串或生产秘密。两者不能为了部署方便合并成一个高权限解析进程。

### 5.5 本地对象存储

建议目录逻辑：

| 目录 | 用途 |
| --- | --- |
| staging | 正在上传或等待验证的临时文件，不可下载 |
| objects/sha256/前两位/后两位/完整摘要 | 已验证的不可变对象 |
| derived | 图片缩略图等可重建派生对象 |
| quarantine | 验证失败且等待短期清理的文件 |

用户原始文件名只作为经清理的显示元数据保存，永远不能组成服务器路径。对象键由服务端生成，最终 APK 以内容摘要寻址。

文件权限建议：

- 目录 0750。
- 文件 0640。
- API/Worker 账户可写，文件网关账户只读。
- 对象目录不位于 Web 根目录。
- 已发布文件不允许覆盖；删除使用延迟回收，不允许直接 unlink 仍被数据库引用的对象。

## 6. 身份认证与会话

### 6.1 两个认证域

普通用户与管理员使用不同的数据表、登录端点、会话表和路由依赖：

- 普通用户令牌不能调用任何 /admin 接口。
- 管理员会话不能伪装为普通用户调用移动端接口。
- 管理员账号与员工手机号账号不通过一个 role 字段混用。

这不是复杂 RBAC，而是减少“角色判断遗漏”造成权限提升的结构性措施。

### 6.2 密码

- 使用 Argon2id 加唯一盐存储，不能可逆加密或使用 SHA-256 直接散列密码。
- 参数以生产服务器上单次验证约 200 至 400 ms 为目标调优，同时不低于 OWASP 当前最低建议。
- 可使用独立于数据库的 pepper 作为纵深防御，保存在仅服务可读的秘密文件中。
- 登录失败统一返回“账号或密码错误”，不暴露手机号是否存在。
- 管理员重置密码生成一次性临时密码，设置 must_change_password，并立即撤销全部会话。
- 修改密码、禁用、重置均递增 auth_version。

### 6.3 移动端会话

建议采用短期不透明访问令牌加轮换刷新令牌，而不是把长期 JWT 当作唯一登录态：

- 访问令牌：256 位随机数，数据库只存 SHA-256，建议 15 分钟。
- 刷新令牌：256 位随机数，建议 30 天，单次使用后轮换。
- 每次 API 请求查会话、账号状态和 auth_version，账号禁用立即生效。
- 刷新令牌复用视为泄露，撤销整个令牌家族。
- 退出登录只撤销当前会话；管理员禁用或重置密码撤销该用户全部会话。

用户量小于 100，数据库会话查询的成本远低于纯 JWT 带来的撤销复杂度。

### 6.4 管理后台会话

- 使用 Secure、HttpOnly、SameSite=Lax 或 Strict 的不透明会话 Cookie。
- 写请求使用独立 CSRF Token，并校验 Origin。
- 绝不把管理员令牌放入 localStorage。
- 建议 30 分钟无操作超时、8 小时绝对超时。
- 发布、下架、改变授权范围、重置密码等操作要求最近 10 分钟内重新验证密码。
- 公网正式使用建议启用管理员 TOTP；不需要双人审批并不等于不需要双因素认证。

### 6.5 登录限流

同时使用两个维度：

1. 网关按源 IP 做短窗口限流，响应 429。
2. 数据库按账号记录连续失败、locked_until 和渐进等待。

成功登录后清零失败计数。安全事件记录账号的内部 ID 或手机号不可逆摘要，不在普通日志中记录完整手机号。

## 7. 授权模型

### 7.1 权限来源

应用授权只能来自以下关系：

用户启用 → 活跃测试组成员关系 → 测试组启用 → 活跃应用授权 → 应用可见

用户属于多个组时取并集。不能把组 ID、应用 ID 或管理员标志直接信任为客户端声明。

### 7.2 中央授权函数

服务层只暴露少量统一授权能力：

| 能力 | 必须检查 |
| --- | --- |
| list_visible_apps | 用户、组、授权和应用均为启用状态 |
| require_app_access | 当前用户存在一条有效授权路径 |
| require_current_download | 应用可见、版本是当前发布版、允许下载、文件 READY |
| require_bug_read | 管理员，或有应用权限且满足 Bug/附件可见规则 |
| require_bug_write | 提交人、应用仍授权，并满足当前 Bug 状态 |
| require_admin | 独立管理员会话且账号启用 |

路由层不得自行复制一段简化 SQL。应用详情、Bug、图片和下载都必须调用同一个授权服务。

对“对象不存在”和“对象存在但无权限”统一返回 404，避免通过 UUID 探测内部应用或 Bug。管理员后台可以返回明确 403，便于操作诊断。

### 7.3 权限变化即时性

- 列表和详情不缓存长时 ACL。
- 下载内容请求再次授权，不能只相信几分钟前获取的详情页。
- 下载会话开始后若账号或版本被停用，新的 Range 请求被拒绝。
- App 下架、组停用、移除成员和撤销应用授权都只更新数据库；下一次请求立即生效。
- 历史下载和 Bug 不随授权撤销而删除。

## 8. 数据模型

所有主键使用 UUID，所有时间使用带时区的 UTC 时间。业务表使用 created_at、updated_at 和 row_version。手机号、标题、说明等长度在数据库和 API 两层限制。

### 8.1 账户与会话

#### user_accounts

- id
- phone_normalized，全局唯一，禁用账号仍占用
- display_name
- password_hash
- status：ACTIVE、DISABLED
- must_change_password
- auth_version
- failed_login_count、locked_until
- created_by_admin_id
- created_at、updated_at、disabled_at
- row_version

#### admin_accounts

- id
- login_name，全局唯一
- display_name
- password_hash
- status、auth_version、failed_login_count、locked_until
- totp_secret_ciphertext，可空
- created_at、updated_at、last_login_at

#### user_sessions

- id、user_id、token_family_id
- access_token_hash、refresh_token_hash，均唯一
- auth_version_snapshot
- access_expires_at、refresh_expires_at
- device_label、client_version
- created_at、last_seen_at、revoked_at、revoke_reason

#### admin_sessions

- id、admin_id、session_token_hash、csrf_secret_hash
- created_at、last_seen_at、absolute_expires_at、revoked_at
- reauthenticated_at

### 8.2 测试组与授权

#### test_groups

- id、name、description
- status：ACTIVE、INACTIVE
- created_by、created_at、updated_at、row_version

#### test_group_memberships

- id、group_id、user_id
- joined_at、left_at
- created_by、revoked_by
- 同一 group_id 与 user_id 只允许一条 left_at 为空的活跃关系

#### application_group_grants

- id、application_id、group_id
- granted_at、revoked_at
- granted_by、revoked_by
- 同一 application_id 与 group_id 只允许一条 revoked_at 为空的活跃授权

保留开始和结束时间能解释历史权限；下载记录仍需保存当时命中的组 ID 快照，不能回头用当前成员关系推断。

### 8.3 应用、文件与版本

#### applications

- id
- package_name，全局唯一，创建后不可更改
- name、short_description、description
- state：DRAFT、PUBLISHED、UNLISTED
- current_version_id，可空
- created_by、created_at、updated_at、row_version

#### file_objects

- id
- object_kind：APK、LOGO、APP_SCREENSHOT、BUG_SCREENSHOT、THUMBNAIL
- object_key，全局唯一且由服务端生成
- sha256、size_bytes、media_type
- width、height，可空
- state：READY、QUARANTINED、DELETING
- original_filename_sanitized，仅展示
- created_at、created_by_realm、created_by_id

只有 READY 对象可被引用和发送。APK 的 sha256 加 size_bytes 建唯一索引可以安全去重；是否对图片去重可按实现简化。

#### upload_jobs

- id
- upload_kind、principal_realm、principal_id
- staging_key
- state：CREATED、RECEIVING、RECEIVED、VALIDATING、COMPLETED、REJECTED、EXPIRED
- expected_size、received_size、computed_sha256
- validation_result JSONB、failure_code、failure_detail_redacted
- created_at、updated_at、expires_at、attempt_count

#### application_media

- id、application_id、file_object_id
- media_kind：LOGO、SCREENSHOT
- sort_order、alt_text
- created_at、removed_at
- 每个应用只允许一个 removed_at 为空的 LOGO

#### application_signing_identities

- id、application_id
- identity_hash：对排序后的全部签名证书 SHA-256 集合再计算摘要
- signer_cert_sha256_set JSONB
- first_version_id
- active、created_at
- 首版每个应用只允许一个活跃签名身份

#### app_versions

- id、application_id、apk_file_object_id
- package_name_snapshot
- version_code：bigint
- version_name
- min_sdk、target_sdk
- signer_identity_hash
- apk_sha256、size_bytes
- parsed_metadata JSONB
- release_notes
- release_state：DRAFT、PUBLISHED、REJECTED、WITHDRAWN
- is_current
- download_enabled
- uploaded_by、created_at、published_at、download_disabled_at
- row_version

关键唯一约束：

- application_id 加 version_code 唯一。
- apk_file_object_id 唯一，防止同一制品作为两个版本发布。
- 只允许一条 is_current 为真的版本。
- is_current 为真时 release_state 必须为 PUBLISHED。

跨表约束通过组合外键或约束触发器保证 current_version、Bug 影响版本和修复版本都属于同一应用。

### 8.4 Bug

#### bug_reports

- id、application_id、affected_version_id、submitter_user_id
- title、description、reproduction_steps
- device_model、android_version、client_version
- visibility：PRIVATE、APP_TESTERS
- status：PENDING、IN_PROGRESS、AWAITING_VERIFICATION、CLOSED
- resolution：FIXED、DUPLICATE、NOT_A_BUG、CANNOT_REPRODUCE、WONT_FIX，可空
- fix_version_id、duplicate_of_bug_id，可空
- created_at、updated_at、closed_at、row_version

#### bug_attachments

- id、bug_id、file_object_id、sort_order
- visibility：PRIVATE、INHERIT
- created_at

截图默认 PRIVATE。INHERIT 只表示跟随 Bug 可见性，不允许比 Bug 本身更公开。

#### bug_replies

- id、bug_id
- author_realm：USER、ADMIN
- author_user_id、author_admin_id，约束为恰有一个非空
- body、created_at

回复只追加，不修改。需要纠错时增加一条更正回复。

#### bug_events

- id、bug_id
- actor_realm、actor_id
- event_type
- from_status、to_status
- payload_redacted JSONB
- created_at

Bug 状态、修复版本、处理结论的改变都必须追加事件。

### 8.5 下载、审计与任务

#### download_events

- id
- client_request_id，与 user_id 组成唯一幂等键
- user_id、application_id、version_id
- authorization_group_ids_snapshot JSONB
- status：STARTED、COMPLETED、FAILED、CANCELLED
- started_at、completed_at
- bytes_expected、bytes_confirmed
- client_sha256
- failure_code
- client_version、device_model、android_version

COMPLETED 的含义固定为“客户端下载完成并校验 SHA-256 后回报”，不等同于安装成功。

#### admin_audit_events

- id、occurred_at
- actor_admin_id，可空以记录失败登录
- action、target_type、target_id
- request_id、source_ip_prefix_or_hash、user_agent_family
- before_redacted JSONB、after_redacted JSONB
- success、failure_code

审计表只允许 INSERT 和 SELECT，不授予运行账户 UPDATE 或 DELETE。密码哈希、令牌、TOTP、截图内容和完整手机号不得进入 before/after。

#### task_jobs

- id、task_type、payload JSONB
- state：PENDING、RUNNING、SUCCEEDED、FAILED、DEAD
- available_at、lease_owner、lease_expires_at
- attempts、max_attempts、last_error_redacted
- created_at、updated_at

#### outbox_events

- id、event_type、aggregate_type、aggregate_id
- payload JSONB、created_at、processed_at、attempts

需要在业务提交成功后异步执行的动作与业务记录在同一事务中写入 Outbox，防止数据库已更新但任务丢失。

#### idempotency_records

- principal_realm、principal_id、route_key、idempotency_key
- request_hash
- response_status、response_reference
- created_at、expires_at
- principal、route 与 idempotency_key 组成唯一键

同一幂等键再次提交相同请求时返回第一次结果；若请求摘要不同则返回 409。记录设置有限保留期，发布、上传完成、下载完成和 Bug 状态变更的保留期应覆盖客户端最大重试窗口。

## 9. 数据库不变量

以下规则必须落在数据库约束或事务中，不能只靠表单校验：

1. 手机号全局唯一。
2. 包名全局唯一且创建后不可修改。
3. 同一应用 version_code 不重复。
4. 同一应用最多一个当前发布版本。
5. 当前版本、Bug 影响版本和修复版本必须属于对应应用。
6. 活跃组成员关系和活跃应用授权不得重复。
7. 一个回复只能有一个作者身份。
8. 已发布版本不能换 APK 文件、包名、版本代码、签名身份或 SHA-256。
9. 已发布 APK 的 file_object 不能删除或改写。
10. Bug CLOSED 必须有 resolution；AWAITING_VERIFICATION 必须有 fix_version_id。
11. resolution 为 DUPLICATE 时必须有关联原 Bug，且两者属于同一应用。
12. 下载 COMPLETED 必须有 completed_at、bytes_confirmed 与 client_sha256。

应用层仍要给出友好错误，但数据库约束是并发条件下的最后防线。

### 10.3 错误语义

- 400：请求格式或状态流转不合法。
- 401：会话无效或过期。
- 403：已认证但后台操作权限不足。
- 404：移动端对象不存在或不可见。
- 409：版本冲突、包名重复、状态已变化、幂等键负载冲突。
- 413：文件或请求体过大。
- 422：字段校验或 APK 元数据不符合业务规则。
- 429：登录或接口限流。

failure_code 使用稳定机器码，detail 是安全的中文说明，不返回堆栈、SQL 或服务器路径。

## 11. APK 上传与校验

### 11.1 两阶段流程

上传与发布必须分开：

1. 管理员创建上传任务，服务端生成 upload_id 和 staging 路径。
2. 网关与 API 按上限流式接收，同时计算 SHA-256；不能一次性读入内存。
3. 文件落入 staging，同步文件和父目录后将任务标记 RECEIVED。
4. 独立 Worker 领取任务，在隔离环境完成 ZIP、Manifest 和签名校验。
5. 校验通过后，在同一文件系统内原子 rename 到内容寻址对象路径。
6. 数据库事务创建 READY file_object 与 DRAFT app_version，完成 upload_job，并写审计和 Outbox。
7. 管理员看到解析结果后单独点击发布。

数据库与文件系统不能做一个原子事务，因此顺序固定为“最终文件先存在，数据库后引用”。若在 rename 后、数据库提交前崩溃，只会留下不可见孤儿文件；对账任务在安全保留期后清理。系统绝不允许出现数据库已经引用但最终文件不存在的版本。

### 11.2 上传输入限制

- APK 只允许一个文件，大小上限配置化；首版建议先按真实样本确定，初始可设 500 MiB。
- Logo、应用截图和 Bug 截图分别设置大小、像素、数量上限。
- 不能只信任扩展名或 Content-Type。
- APK 检查 ZIP magic、中央目录、条目数量、单条目和总解压大小。
- 拒绝绝对路径、父目录穿越、重复危险条目、异常压缩比和加密 ZIP。
- 图片只允许 JPEG、PNG、WebP 中已验证可安全重编码的格式；首版不接收 SVG、HTML、PDF 或动图。
- 上传超时或失败文件进入过期清理，不进入对象目录。

### 11.3 APK 工具链

使用 Android SDK 官方工具，固定版本并记录到解析结果：

- apksigner verify --verbose --print-certs：验证签名方案并读取签名证书。
- aapt2 dump badging 或 apkanalyzer manifest：读取包名、versionCode、versionName、minSdk、targetSdk 等。

调用规则：

- 参数数组直接传给子进程，禁止 shell 拼接。
- 设置 CPU、内存、文件大小、进程数和执行时间上限。
- Parser 账户不访问数据库密码、生产秘密和 sing-box 文件。
- Parser 默认无出站网络。
- 记录工具退出码和安全化错误，不把攻击文件生成的超长输出写入日志。

### 11.4 签名连续性

首版采用保守的“签名证书集合完全相同”规则：

1. 首个发布版本必须通过 apksigner 验证。
2. 记录所有 signer 证书 SHA-256，排序后生成 identity_hash。
3. 首次发布时该集合成为应用签名信任锚。
4. 后续版本必须与信任锚完全相同；多签名不能只匹配其中一个。
5. 未签名、校验失败、证书集合变化一律拒绝发布。

Android v3 签名证书轮换的 proof-of-rotation 不在首版支持范围。这样会拒绝某些合法密钥轮换，但不会误把陌生密钥当成可覆盖更新。确需轮换时应作为独立迁移项目设计，而不是管理员绕过校验。

如果团队还没有正式签名，可使用一把稳定保管、可备份的内部测试签名。平台只保存证书摘要，不保存 keystore、私钥或私钥密码。每次构建随机生成签名会使 Android 无法覆盖升级，必须禁止。

### 11.5 版本规则

- package_name 必须与应用固定包名完全一致。
- versionCode 必须大于该应用所有已发布 versionCode。
- app_id 加 versionCode 不允许重复，即使旧草稿已撤回也不能无痕复用。
- 拒绝 android:testOnly 为真且普通设备无法正常安装的制品。
- 记录 minSdk、targetSdk、ABI、签名方案、证书摘要和 APK SHA-256。
- 首版不因权限变化自动拒绝，但解析结果中应保存权限列表并在后台展示。

“未接恶意代码扫描”是明确残余风险，不等于跳过结构、签名、包名、版本和完整性校验。

## 12. 图片安全与隐私

图片上传后必须解码再重编码，不能原样公开发送：

- 校验实际格式、尺寸、总像素和帧数，防止解压炸弹。
- 纠正方向后删除 EXIF、GPS 和其他元数据。
- 输出为平台控制的 JPEG、PNG 或 WebP。
- 为列表生成受限尺寸缩略图，避免加载原始大图。
- 对输出重新计算 SHA-256。
- 设置 Content-Type、Content-Disposition: inline、X-Content-Type-Options: nosniff。
- 图片 URL 不包含用户原始文件名或手机号。
- Bug 截图每次访问仍走权限校验；浏览器缓存使用 private 策略。

管理员将 Bug 从 PRIVATE 改为 APP_TESTERS 时，截图不会自动公开，必须逐张明确改为 INHERIT。

## 13. 下载流程与统计口径

### 13.1 下载开始

1. 客户端针对当前 version_id 发送 client_request_id。
2. 服务端验证用户、组、应用、当前版本、download_enabled 和 APK 文件状态。
3. 在事务中创建或幂等返回 download_event，保存授权命中的组快照。
4. 客户端访问该事件的 content 端点并携带当前访问令牌。
5. content 端点再次授权后通过 X-Accel-Redirect 发送文件，支持 Range、取消和重试。

下载地址不是永久公开对象 URL。download_id 是随机 UUID，但 UUID 不是权限；访问仍需要与事件 user_id 匹配的有效会话。

### 13.2 下载完成

客户端完成文件写入后：

1. 计算下载文件 SHA-256。
2. 与服务端版本摘要比较。
3. 相同才调用 complete。
4. 服务端只允许事件所属用户幂等完成，并核对报告的 SHA-256 和字节数。

Nginx 发完响应不能证明 Android 已把文件完整保存，因此不以服务器 200 或发送字节数作为完成口径。客户端回报可能缺失，所以后台需同时展示“开始次数”和“确认完成次数”。

## 14. 关键事务

### 14.1 发布版本

一个数据库事务内执行：

1. 用 SELECT FOR UPDATE 锁定 application 行。
2. 重新读取草稿版本、READY 文件、签名身份和最大已发布 versionCode。
3. 校验应用状态、包名、签名、versionCode 与当前版本。
4. 将旧当前版本 is_current 设为 false。
5. 将新版本设为 PUBLISHED、is_current=true、download_enabled=true。
6. 更新 application.current_version_id 和 state。
7. 写 admin_audit_event 和 outbox_event。
8. 提交。

唯一部分索引保证并发请求最终也不能产生两个当前版本。重复发布使用同一 Idempotency-Key 时返回第一次结果，不产生第二条审计。

### 14.2 撤销授权、禁用用户与下架

- 变更业务行、递增 row_version、写审计和 Outbox 在同一事务。
- 禁用或重置用户同时递增 auth_version 并撤销全部会话。
- 下架只改变应用可见性和下载能力，不删除版本、Bug、下载或文件。
- 不创建长期可用下载令牌，因此无需遍历删除公开链接。

### 14.3 Bug 状态

更新时锁定 bug_reports 行或校验 row_version：

| 当前状态 | 操作者 | 允许下一状态 | 附加要求 |
| --- | --- | --- | --- |
| PENDING | 管理员 | IN_PROGRESS | 追加状态事件 |
| PENDING | 管理员 | CLOSED | resolution 必填 |
| IN_PROGRESS | 管理员 | AWAITING_VERIFICATION | fix_version 必填且属于同一应用 |
| IN_PROGRESS | 管理员 | CLOSED | resolution 必填 |
| AWAITING_VERIFICATION | 提交人 | CLOSED | 表示验证通过，resolution=FIXED |
| AWAITING_VERIFICATION | 提交人 | IN_PROGRESS | 表示仍存在，追加说明 |
| CLOSED | 管理员 | IN_PROGRESS | 必填重开原因 |

用户只能在 PENDING 且管理员尚未开始处理前修改标题、描述和复现步骤；之后只能追加回复。状态更新、回复、Bug 事件和审计在同一事务。

### 14.4 文件删除

不直接删除业务文件：

1. 确认没有活跃或历史强引用。
2. 标记 DELETING 并进入延迟队列。
3. 等待时间必须覆盖最近一次可用备份。
4. Worker 删除文件后再完成数据库清理。

APK 只要被任何已发布版本引用就永久保留，除非以后建立明确的数据保留与归档政策。

## 15. 管理审计

必须审计：

- 管理员登录成功、失败、退出和重认证。
- 创建、编辑、启用、禁用、重置用户。
- 创建、停用测试组，增删成员和应用授权。
- 创建、编辑、下架应用。
- 上传结果、APK 校验失败、发布、停止下载。
- Bug 可见性、状态、修复版本、处理结论和回复。
- 备份、恢复演练、权限异常和配置变更。

审计写入必须满足：

- 成功业务操作与审计事件同事务提交。
- 只追加，不允许普通运行账户更新或删除。
- before/after 只保存必要字段并脱敏。
- 每条事件带 request_id，能与结构化应用日志关联。
- 失败登录和被拒绝的高风险操作写 security event，但不记录输入密码、令牌或截图内容。

若以后需要防数据库超级管理员篡改，可每天对审计序列生成摘要并写入异机不可变存储。当前无监管要求，首版先保证数据库权限和异机备份。

## 16. 威胁模型

### 16.1 关键资产

- APK 制品、SHA-256、包名和签名身份。
- 员工手机号、密码哈希和会话。
- Bug 描述、设备信息和截图。
- 测试组与应用授权关系。
- 下载记录和管理员审计。
- 数据库、对象存储和备份凭据。
- 同主机 sing-box 的配置、密钥、端口、路由和运行稳定性。

### 16.2 攻击者

- 未认证公网攻击者。
- 获得普通员工账号的攻击者。
- 恶意或被攻陷的员工设备。
- 被攻陷的管理员浏览器或管理员账号。
- 上传恶意 APK/图片的管理员账号。
- 利用服务漏洞取得本平台进程权限的攻击者。
- 误操作部署人员。

### 16.3 STRIDE 与缓解

| 编号 | 类别 | 威胁 | 严重度 | 主要控制 | 残余风险 |
| --- | --- | --- | --- | --- | --- |
| T01 | 欺骗 | 密码喷洒、撞库、手机号枚举 | 高 | Argon2id、统一错误、IP 和账号双限流、管理员 TOTP、事件告警 | 员工复用弱密码仍可能失陷 |
| T02 | 欺骗 | 访问或刷新令牌被盗 | 高 | TLS、不透明随机令牌、数据库只存摘要、短访问期、刷新轮换与复用检测、立即撤销 | 被控设备上的安全存储也可能被读取 |
| T03 | 篡改 | 已发布 APK 被原地替换 | 严重 | 内容寻址、只读对象、已发布字段不可改、SHA-256、客户端校验、审计 | 主机 root 被攻陷仍可同时篡改文件与数据库 |
| T04 | 篡改 | 恶意新版本冒充正常更新 | 严重 | 签名证书集合完全匹配、versionCode 递增、高风险重认证、审计 | 无恶意代码扫描，持有合法签名密钥的恶意包无法识别 |
| T05 | 篡改 | 并发发布产生两个当前版本 | 高 | application 行锁、事务、唯一部分索引、幂等键 | 数据库管理员绕过约束属于主机级风险 |
| T06 | 否认 | 管理员否认发布、下架或授权变更 | 高 | 同事务追加审计、request_id、异机备份 | 首版审计不是外部可信时间戳 |
| T07 | 信息泄露 | 猜测 ID 查看未授权应用或 Bug | 严重 | 中央授权函数、服务端 Join 校验、移动端统一 404、负向权限测试 | 业务文案本身仍需避免泄密 |
| T08 | 信息泄露 | APK 或截图形成永久公开 URL | 严重 | 对象目录不公开、internal location、每次内容请求鉴权、private cache | 用户下载后仍可自行转发 APK，BYOD 无法阻止 |
| T09 | 信息泄露 | Bug 截图含定位、账号或聊天内容 | 高 | 提交提示、EXIF 清除、默认 PRIVATE、管理员可见性分离 | 无法自动识别图片里的全部敏感文字 |
| T10 | 信息泄露 | 日志泄露密码、Cookie、手机号、路径 | 高 | 结构化日志脱敏、网关不记敏感头、错误输出清理、访问控制 | 调试模式误开仍有风险，生产必须禁用 |
| T11 | 拒绝服务 | 大文件、慢上传、压缩炸弹耗尽磁盘或 CPU | 高 | 请求上限、超时、配额、流式写入、ZIP 结构限制、Worker 资源限制、staging TTL、磁盘告警 | 同机磁盘仍是共享有限资源 |
| T12 | 权限提升 | 普通令牌调用管理员接口 | 严重 | 独立认证域、独立会话表、独立路由依赖、权限测试 | 管理员 API 自身漏洞仍需代码审查 |
| T13 | 权限提升 | 通过路径穿越读写任意文件 | 严重 | 服务端对象键、内容寻址、不使用原始文件名、internal alias 固定根、无任意路径 API | 主机级漏洞不在应用路径控制范围内 |
| T14 | 权限提升 | APK 或图片解析器 RCE | 严重 | 独立低权限 Worker、无网络、资源上限、固定工具链、无 shell、最小目录权限 | Android 工具链或图像库仍可能有未知漏洞 |
| T15 | 篡改 | 越权修改 Bug 状态或修复版本 | 高 | 明确状态机、行锁/row_version、同应用组合外键、事件时间线 | 管理员本身可合法作出错误判断 |
| T16 | 信息泄露 | CSRF/XSS 窃取后台能力 | 高 | HttpOnly Cookie、CSRF、Origin、CSP、输出编码、禁内联脚本、依赖扫描 | 管理员浏览器扩展或终端被控仍有风险 |
| T17 | 篡改 | SQL 注入或过度查询 | 严重 | 参数化 ORM/SQL、Pydantic 输入、数据库最小权限、分页和查询上限 | 手写动态 SQL 需专项审查 |
| T18 | 信息泄露 | 备份被窃取 | 严重 | 客户端侧加密、异机存储、独立密钥、最小访问、恢复审计 | 密钥与备份同时泄露时数据暴露 |
| T19 | 拒绝服务 | 部署改变防火墙、端口或路由导致 sing-box 中断 | 严重 | 部署前只读盘点、保护清单、禁止 host network/CAP_NET_ADMIN/TUN、端口冲突门禁、独立回滚 | 同一主机内核和磁盘故障仍会同时影响两者 |
| T20 | 拒绝服务 | 对象与数据库不一致导致版本不可下载 | 高 | 最终文件先落盘、DB 后引用、状态机、对账 Worker、备份恢复校验 | 人工绕过应用直接改文件仍可能破坏 |

### 16.4 明确接受的风险

1. **无恶意代码扫描**：平台只能确认制品结构、签名归属和完整性，不能证明 APK 没有恶意行为。
2. **单机单点**：本地 PostgreSQL 与对象目录随主机故障一起不可用；备份解决恢复，不解决即时高可用。
3. **BYOD 转发**：授权可以阻止平台下载，但无法阻止员工转发已下载 APK。
4. **安装不可观测**：客户端下载完成不代表系统安装成功。
5. **主机 root 风险**：一旦目标服务器 root 被攻陷，平台和同机服务都无法提供强隔离保证。

若这些风险超出业务接受范围，应增加恶意代码扫描、独立服务器/对象存储、管理员 MFA 和更强终端管理，而不是用应用代码伪装已解决。

## 17. 与 sing-box 共存的部署隔离

### 17.1 不可触碰清单

部署前要通过只读盘点确认并登记：

- sing-box 的服务单元、容器或进程。
- 二进制、配置、证书、密钥和运行目录。
- 监听端口、TUN 设备、路由、策略路由、DNS 和防火墙/NAT 规则。
- 服务用户、环境文件、自动更新与重启策略。
- 当前公开入口是否已经占用 80/443。

以上对象在本项目变更中一律禁止写入、覆盖、移动、重载、重启或共用。本文和代码仓库不得保存 root 密码；正式部署应改用独立部署账户与 SSH 密钥，并更换任何已经通过聊天等渠道暴露的高权限密码。

### 17.2 部署前门禁

按顺序执行：

1. 只读记录系统版本、磁盘、内存、现有监听、服务和容器。
2. 导出当前防火墙、路由和 DNS 状态作为基线，但不做修改。
3. 确认 sing-box 健康检查、出口 IP 和关键端口基线。
4. 选择没有冲突的回环端口或 Unix Socket。
5. 明确公网 HTTPS 的接入方式。
6. 在变更清单上证明不需要改 sing-box 配置。

若 443 已由 sing-box 占用，禁止停止或替换它来让 Nginx 绑定。可选方案只有：

- 接入已经存在的 L7 反向代理；
- 使用独立公网 IP；
- 使用明确对外公布的其他 HTTPS 端口；
- 在另一个主机部署平台。

任何需要修改 sing-box SNI 分流或 fallback 的方案都属于独立网络变更，不能夹带在应用部署中。

### 17.3 平台目录与账户

建议逻辑隔离：

- 独立运行账户 betaapp，无登录 Shell 或仅受限 Shell。
- 独立只读文件网关账户。
- 独立数据库账户：migration_owner、app_runtime、backup_reader。
- 应用目录、数据目录、配置目录、备份暂存目录均使用 internal-beta 命名空间。
- 应用账户没有读取 sing-box 目录的权限。
- Parser Worker 没有 sudo、NET_ADMIN、NET_RAW、SYS_ADMIN，也不访问 /dev/net/tun。

### 17.4 容器选择

不要为了本项目在未知主机上直接安装 Docker。Docker 安装和桥接网络可能改变 iptables/NAT，从而影响 VPN。

- 如果服务器已经稳定运行 Docker，且盘点证明 Docker 网络与 sing-box 共存，可使用独立 Compose project、独立 bridge、独立 volume；禁止 network_mode: host、privileged、CAP_NET_ADMIN 和宿主机 /etc 挂载。
- 如果服务器没有 Docker，默认优先使用 Python 虚拟环境、独立 systemd 单元、PostgreSQL 本地 Socket 和回环 Nginx，避免引入新的防火墙管理者。
- 无论哪种形态，停止平台只能停止平台自己的单元或 Compose project，绝不能使用全局 Docker 清理或模糊匹配 systemctl 命令。

### 17.5 网络暴露

- PostgreSQL 仅监听 Unix Socket、回环地址或私有容器网络，不公开 5432。
- FastAPI 仅监听回环地址、Unix Socket 或私有网络，不直接公网暴露。
- 对象目录没有独立端口。
- 只有经过确认的 HTTPS 入口可公网访问。
- 管理后台可进一步限制来源 IP 或通过单独域名暴露，但不能依赖它替代管理员认证。
- 不修改系统默认路由、DNS、TUN 或全局转发开关。

### 17.6 上线与回滚

上线前：

- 备份数据库、对象和当前平台配置。
- 验证 Nginx 配置和应用配置。
- 在回环端口完成健康检查与冒烟测试。
- 再执行最小入口变更。

回滚只恢复平台的上一制品、配置和数据库兼容版本。数据库迁移采用 expand/contract 策略；有破坏性迁移时必须先验证恢复。回滚过程不得重启 sing-box。

上线后对比部署前后的 sing-box 进程、端口、路由、出口 IP 与错误日志。任何变化都视为发布失败并立即回滚平台变更。

## 18. 备份与恢复

### 18.1 备份目标

- 建议 RPO：6 小时以内。
- 建议 RTO：4 小时以内。
- 至少一份备份位于目标服务器之外并加密。
- 备份密钥不能只保存在目标服务器。

### 18.2 备份内容

- PostgreSQL 自定义格式逻辑备份。
- 完整 objects 目录；staging、quarantine 和 derived 可不作为核心备份，derived 可重建。
- 数据库迁移版本和部署制品版本。
- 脱敏后的运行配置模板。
- Nginx 平台站点配置。
- 备份清单、对象数量、总字节、数据库校验结果。

生产秘密单独加密备份，不能和明文配置一起打包。

### 18.3 一致性策略

最终对象先落盘，数据库后引用且对象不可变，因此可以使用以下安全顺序：

1. 生成时点 T 的 PostgreSQL 逻辑备份。
2. 对数据库备份、objects 和平台配置执行同一次加密快照。
3. T 之后新建但同时被快照捕获的对象至多成为恢复后的孤儿，不会造成 T 时刻数据库引用缺文件。

备份作业必须验证：数据库备份可读取、对象目录可遍历、空间足够、异机上传成功。只有创建了文件不算成功。

建议保留 14 个日备份、8 个周备份和 12 个每月备份；实际期限可因空间和公司政策调整。

### 18.4 恢复步骤

1. 在隔离环境安装与备份清单一致的应用版本和数据库主版本。
2. 恢复 objects 与配置，不开放公网。
3. 恢复 PostgreSQL。
4. 执行数据库迁移兼容检查。
5. 对所有已发布 APK 和数据库引用图片做存在性检查；APK 全量重算 SHA-256。
6. 检查每个应用最多一个当前版本、所有 Bug 版本归属和授权关系。
7. 用管理员与已授权/未授权测试账号执行冒烟测试。
8. 只在验证通过后切换入口。

至少每月自动恢复到临时数据库并跑完整性检查，每季度做一次包含真实对象文件的人工恢复演练。每次恢复演练形成审计记录和耗时。

## 19. 可观测性与运维

### 19.1 日志

- JSON 结构化日志，统一 request_id、route、status、latency_ms、principal_realm 和内部 principal_id。
- 不记录密码、令牌、Cookie、完整手机号、APK 内容、截图内容和数据库连接串。
- 上传解析错误截断长度并移除服务器绝对路径。
- 网关、API、Worker、备份和对账任务分别记录。

### 19.2 指标

- 登录成功、失败、限流和账号锁定。
- API QPS、P50/P95/P99、4xx、5xx。
- 数据库连接池、慢查询、锁等待。
- 上传字节、失败、staging 数量和年龄。
- APK 校验通过/拒绝及拒绝原因。
- Worker 队列长度、任务年龄、重试和 DEAD 数量。
- 下载开始、完成、失败及完成率。
- 对象目录使用量、inode、剩余空间。
- 备份年龄、大小、上传和恢复验证状态。

### 19.3 告警

至少告警：

- 5xx 持续升高。
- 登录失败突增或管理员账号锁定。
- Worker 最老任务超过 5 分钟。
- 磁盘剩余低于 20% 或按增长率预计 7 天内耗尽。
- 最近成功异机备份超过 8 小时。
- 数据库无法连接、对象缺失或摘要不一致。
- 发布后大量下载摘要失败。
- 平台部署前后 sing-box 健康基线发生变化。

## 20. 容量与性能

### 20.1 初始进程

在未获得服务器资源数据前，建议从以下最小配置开始：

- 2 个 FastAPI Worker。
- 1 个 APK/图片 Worker。
- PostgreSQL 连接池每个 API Worker 5 个连接，保留管理与备份连接。
- Nginx sendfile 与 Range。

不要按用户只有 100 人就把 APK 下载并发算作 1。版本发布后可能集中下载，文件传输必须与 API 进程隔离。

### 20.2 存储估算

对象容量至少按以下公式规划：

应用数 × 平均保留版本数 × 平均 APK 大小  
+ 应用截图和 Bug 截图  
+ 30% 文件系统余量  
+ 同机备份暂存空间

当磁盘预计 90 天内达到 70% 时，应扩容或迁移对象存储。不能依赖临时清理已发布 APK 来腾空间。

### 20.3 数据库索引

重点索引：

- 用户 phone_normalized 唯一。
- 应用 package_name 唯一。
- 活跃成员和活跃授权部分唯一索引。
- app_versions(application_id, version_code) 唯一。
- app_versions(application_id) where is_current=true 唯一。
- Bug 按 application_id、status、affected_version_id、submitter_user_id、created_at。
- 下载按 user_id、version_id、started_at、status。
- 审计按 occurred_at、actor_admin_id、target_type 加 target_id。
- 任务按 state、available_at。

列表统一 keyset 分页，避免在下载和审计记录增长后使用大 OFFSET。

## 21. 三轮服务端独立验证门禁

本文只定义服务端门禁，执行时每一轮由不同测试清单或独立审查者签字，不能把同一组测试重复运行三次当作三轮。

### 第一轮：功能与事务

- 账户、组、授权、应用、版本、素材、Bug、下载和审计全部 API 集成测试。
- 授权矩阵包含已授权、未授权、组停用、用户禁用、应用下架、下载停止。
- APK 未签名、包名错、签名错、versionCode 未递增、文件损坏全部拒绝。
- 并发发布 20 次仍只有一个当前版本。
- Bug 每条合法/非法状态边都覆盖。
- 幂等键、row_version、上传中断和 Worker 重试覆盖。

### 第二轮：安全、恢复与部署隔离

- OWASP API 权限负向用例、IDOR、CSRF、XSS、SQL 注入、路径穿越和令牌撤销。
- APK ZIP 炸弹、异常条目、解析超时；图片像素炸弹、伪 MIME、EXIF 清除。
- 管理员与用户令牌交叉调用全部失败。
- 对象目录不能通过公网路径直接枚举。
- 完成一次从异机备份到隔离环境的全量恢复，并逐个校验 APK 摘要。
- 部署前后对比 sing-box 进程、端口、路由、出口 IP 和健康状态，必须完全无变化。

### 第三轮：压力、耐久与用户界面链路

- 20 并发普通 API 请求下验证 P95 与错误率目标。
- 20 并发 Range 下载期间普通 API P95 不高于 1 秒。
- 并发上传和下载时磁盘、连接池与 Worker 队列不失控。
- 至少 1 小时混合负载，检查内存、临时文件、连接和任务租约泄漏。
- 管理后台通过真实浏览器覆盖上传进度、校验失败、发布冲突、权限拒绝、Bug 状态与下载查询。
- 服务重启、Worker 中断、数据库短暂不可用后任务可恢复且无重复发布。

每轮都必须保留测试环境、版本、命令、原始结果、失败项和修复后的复验记录。最终验收不是“所有现有测试变绿”，而是逐条证明需求分析第 14 节的十个 MVP 场景和本文安全门禁。

## 22. 实施顺序

1. 建立数据库迁移、运行账户与最小权限。
2. 实现认证域、会话撤销、用户和测试组。
3. 实现中央应用授权查询及负向测试。
4. 实现文件状态机、受控存储和图片 Worker。
5. 实现 APK Worker、签名身份与版本草稿。
6. 实现发布事务、下架和停止下载。
7. 实现 Nginx 内部下载与下载完成回报。
8. 实现 Bug 状态机、附件隐私、回复和时间线。
9. 实现管理审计、Outbox、对账与清理。
10. 实现备份、恢复、监控和部署门禁。
11. 完成三轮服务端验证后，再进入 Android 客户端联调。

## 23. 开发前仍需确定

以下问题不会改变总体架构，但会改变配置或产品表现：

1. 管理员是否在首版启用 TOTP。
2. Bug 文本是否默认对同应用测试者公开；本文采用 PRIVATE。
3. 客户端最低 Android 版本。
4. 实际 APK、Logo 和截图大小上限。
5. 正式域名、证书与 80/443 当前占用情况。
6. 目标服务器是否已有 PostgreSQL、Nginx、Docker 或其他入口。
7. 异机备份目标及备份密钥保管人。
8. 日志、Bug、下载和已下架 APK 的业务保留期限。

这些问题不能通过猜测目标服务器现状解决。首次连接服务器只做只读盘点，不直接安装软件、开放端口或修改防火墙。
