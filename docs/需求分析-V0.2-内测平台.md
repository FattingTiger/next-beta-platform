# Android 内部应用内测与分发平台需求分析 V0.2

> 状态：根据业务方补充信息修订的讨论稿  
> 日期：2026-08-28  
> 本文只定义产品需求、业务规则和首版边界，不涉及技术选型与代码实现。

## 1. 项目定位

本项目是一个面向公司内部员工的小规模 Android 应用内测平台，主要解决内部 APK 的集中管理、按测试组分发、版本展示、下载记录和 Bug 闭环问题。

平台由三部分组成：

1. **Android 内测客户端**：测试员工登录后查看自己有权测试的应用，下载 APK，并提交、查看 Bug 反馈。
2. **Web 管理后台**：管理员维护用户和测试组，上传、更新和下架 APK，维护应用资料和截图，处理 Bug。
3. **服务端**：保存应用、版本、用户、测试组、Bug、附件和下载记录，并负责登录、权限校验和文件下载。

本项目不是公开商业应用市场，也不是企业设备管理系统。首版不解决静默安装、强制升级、远程卸载、设备纳管和大规模应用分发。

## 2. 已确认的业务条件

| 项目 | 已确认结论 |
| --- | --- |
| 用户规模 | 内测用户不超过 100 人 |
| 设备来源 | 员工自有 Android 手机，非统一配发 |
| 设备管理 | 无 MDM，无定制 ROM，不纳管设备 |
| 部署环境 | 公网部署，员工可在外网访问和下载 |
| 用户范围 | 仅公司内部员工，不允许外包或合作方账号 |
| 账户来源 | 管理员在后台创建，账号与手机号绑定 |
| 应用上传 | 只有管理员可以上传和更新 APK |
| 审批流程 | 暂不需要双人审核或独立审批角色 |
| 可见范围 | 通过测试用户组控制，每个用户只看到所属组被授权的应用 |
| 发布通道 | 暂不区分测试、灰度和正式通道 |
| 安装策略 | 不要求静默安装、强制升级或远程卸载 |
| 更新提醒 | 暂不做推送提醒；用户打开客户端时可看到是否有新版本 |
| 文件场景 | 不考虑超大 APK、弱网、海外和专网 |
| 安全检测 | 首版不接入现有恶意代码扫描系统 |
| 数据要求 | 记录用户是否下载；无数据出境和监管审计留存要求 |
| Bug 反馈 | 客户端支持截图、文字说明、处理状态查询 |

## 3. 产品目标与成功标准

### 3.1 产品目标

- 管理员能够在一个后台中管理全部内测应用和版本。
- 管理员能够通过测试组准确控制应用的可见用户。
- 测试员工能够方便地查看应用介绍、版本、截图和更新内容并完成下载。
- 测试员工能够围绕具体应用和版本提交带截图的 Bug。
- 管理员能够处理 Bug，测试员工能够查看处理进展和结果。
- 平台能够回答“哪个用户在什么时间下载了哪个应用的哪个版本”。

### 3.2 首版成功标准

- 管理员发布一个应用后，授权组成员能够看到并下载，非授权成员无法查看或下载。
- 新版本发布后，客户端能够展示最新版本和更新内容，并提供“更新”操作。
- 用户可以在较短步骤内完成 Bug 提交，管理员可以更新状态并回复。
- 下载、Bug、应用版本和用户之间的关系可以在后台检索。
- 系统在 100 个以内账户、低并发下载场景下稳定运行。

## 4. 用户角色

### 4.1 内测用户

- 使用管理员创建的账号登录。
- 查看所属测试组被授权的应用。
- 查看应用资料、版本、应用截图和版本更新内容。
- 下载 APK，并按 Android 系统流程手动确认安装。
- 查看该应用的 Bug 及处理情况。
- 提交带截图和说明的 Bug。
- 查看自己提交的 Bug、管理员回复和处理状态。

### 4.2 管理员

- 创建、编辑、禁用内测用户，绑定手机号和分配测试组。
- 创建、编辑和停用测试组，维护组内成员。
- 创建应用、上传 APK、维护应用资料、截图和版本更新内容。
- 设置应用对哪些测试组可见。
- 发布新版本、下架应用或停止某个版本的下载。
- 查看全部 Bug，修改处理状态、填写回复和处理结论。
- 查看用户、应用和版本维度的下载记录。

首版只有“内测用户”和“管理员”两类角色，不建设复杂的后台权限矩阵。应至少保留管理员操作记录，以便出现误操作时追溯。

## 5. 核心业务对象

| 对象 | 关键内容 |
| --- | --- |
| 用户 | 姓名、唯一手机号、登录凭据、账号状态、所属测试组、创建时间 |
| 测试组 | 组名、说明、成员、可见应用、状态 |
| 应用 | 应用名称、包名、Logo、简介、应用截图、当前版本、可见测试组、状态 |
| 应用版本 | APK 文件、版本名称、版本代码、文件大小、更新内容、上传时间、发布状态 |
| Bug | 所属应用和版本、提交人、标题、描述、截图、设备信息、状态、处理结论 |
| Bug 回复 | 回复人、回复内容、时间、关联 Bug |
| 下载记录 | 用户、应用、版本、下载开始/完成状态、时间、必要的设备信息 |
| 管理操作记录 | 管理员、操作对象、操作类型、时间、结果 |

关系规则：

- 一个用户可以属于一个或多个测试组。
- 一个测试组可以看到一个或多个应用。
- 一个应用可以授权给一个或多个测试组。
- 一个应用可以拥有多个历史版本，但客户端默认只提供当前发布版本下载。
- 每个 Bug 必须关联到具体应用和具体版本，避免版本更新后无法判断问题出现在哪一版。

## 6. Android 客户端功能需求

### 6.1 设计定位

**设计解读：** 这是一个面向公司员工、用于应用发现和测试反馈的 Android 工具，视觉上采用简洁、内容优先、接近 iOS App Store 的展示方式，同时遵循 Android 的导航、权限和安装习惯。

建议设计参数：

- 视觉差异度：5/10，具有 App Store 式内容层级，但不照搬 iOS 控件。
- 动效强度：2/10，以系统转场、下载进度和状态反馈为主。
- 信息密度：4/10，保持清晰留白，Bug 列表和后台操作保持实用。
- 使用系统字体和一套克制的品牌主色；状态颜色只用于成功、处理中、错误等语义。
- 所有可点击区域不小于 Android 建议的 48dp，并支持系统字体放大和深色模式。

### 6.2 登录

#### 首版建议方式

- 管理员创建用户并绑定唯一手机号。
- 用户使用“手机号 + 密码”登录。
- 用户不能自行注册。
- 管理员可以重置密码、禁用账号或解除登录会话。
- 登录成功后保存安全登录态，过期后重新登录。
- 账号被禁用后，现有登录态应失效，不能继续获得应用或下载地址。

手机号只是账号标识还是需要短信验证码，尚未最终确认。考虑首版规模较小，默认采用手机号加密码，避免引入短信服务；以后可增加短信验证码登录或找回密码。

#### 页面状态

- 正常输入、提交中、账号不存在/被禁用、密码错误、网络错误和登录过期。
- 密码错误不能暴露过多账户信息；公网登录需要限制高频尝试。
- 错误后保留手机号，密码由用户重新输入。

### 6.3 应用首页

- 显示当前用户有权限测试的应用，不展示无权限应用。
- 每个应用条目展示 Logo、名称、当前版本、简短说明和主要按钮。
- 根据本机状态显示“获取”“打开”或“更新”；若无法可靠判断是否安装，至少显示“下载”。
- 应用数量较少时采用清晰列表；数量增加后提供搜索。
- 支持下拉刷新。
- 无应用时明确提示“当前没有分配给你的内测应用”，而不是空白页面。
- 网络失败时提供重试；已加载内容可在短时间内保留，但下载前必须重新校验权限。

### 6.4 应用详情

首屏需要让用户在五秒内确认“这是什么应用、当前版本是什么、下一步如何下载”。

页面内容按以下顺序组织：

1. Logo、应用名称、当前版本、文件大小和“获取/更新”按钮。
2. 应用简介。
3. 应用截图横向浏览区域。
4. 当前版本更新内容和发布时间。
5. Bug 反馈入口。
6. Bug 列表及处理状态。
7. 历史版本信息只读展示（可后置，不默认提供旧版下载）。

应用截图与 Bug 截图要明确区分：前者是管理员维护的产品展示素材，后者是测试用户提交的问题附件。

### 6.5 下载和安装

- 点击下载前，服务端再次检查账号状态、测试组权限和应用状态。
- 客户端展示文件大小、下载进度、成功、失败、取消和重试状态。
- 记录下载开始和下载完成；首版统计以“客户端确认文件下载完成”为下载成功口径。
- Android 8.0 及以上设备首次安装时，用户需要授权该客户端“安装未知应用”。
- 下载完成后由客户端调起 Android 系统安装界面，用户手动确认安装。
- 客户端应处理用户取消、安装权限未开启、文件损坏、签名冲突、存储空间不足和系统版本不兼容等常见情况。
- 不承诺记录最终安装成功，因为员工设备未被纳管，系统和厂商行为存在差异；本项目已确认的统计需求只到下载完成。
- 新版本发布后不推送提醒；用户打开应用列表或详情时看到“更新”状态和更新内容。

### 6.6 Bug 反馈

Bug 反馈是首版核心功能，不作为普通“意见留言”处理。

#### 新建 Bug

用户从具体应用详情进入“反馈 Bug”，系统自动带入：

- 应用名称和包名。
- 当前发布版本；如果能识别本机已安装版本，则优先带入已安装版本并允许用户确认。
- 提交用户和提交时间。
- 手机型号和 Android 版本，提交前告知用户并允许查看这些信息。

用户填写：

- Bug 标题，必填。
- 问题描述，必填。
- 复现步骤，首版可作为选填项。
- 截图，支持多张，建议首版限制为 1～5 张常见图片格式。

提交按钮必须有上传中、成功、失败和重试状态。网络失败时应保留已填写内容，避免重新输入。

#### 截图方式与边界

- 首版采用“用户使用手机系统截图，再从相册选择图片上传”。
- 可同时提供系统分享入口，让用户从相册或截图通知中把图片分享至内测平台；可作为 P1 增强。
- 不在首版中实现持续悬浮窗、辅助功能监听或后台截取其他应用画面，避免引入高权限、兼容性和隐私问题。
- 上传前提示用户检查截图中是否包含手机号、聊天内容、账号、密码或其他个人信息。

#### Bug 查看

- “我的反馈”展示本人提交的全部 Bug，按最新进展排序。
- 应用详情展示与该应用相关的 Bug 标题、版本和处理状态，帮助测试人员避免重复提交。
- 推荐默认让同一应用的授权测试用户看到 Bug 基本内容和处理状态，不显示提交人的手机号等账户信息。
- 管理员需要能够将包含敏感信息的 Bug 或截图设置为仅提交人和管理员可见。
- Bug 详情展示描述、截图、版本、状态时间线、管理员回复和处理结论。

#### Bug 状态

首版使用四个主状态，避免流程过重：

1. **待处理**：用户已提交，管理员尚未开始处理。
2. **处理中**：管理员已确认并正在跟进。
3. **待验证**：管理员认为问题已在某个版本修复，等待测试用户验证。
4. **已关闭**：处理完成或无需继续。

关闭时需要选择处理结论：已修复、重复问题、非 Bug、无法复现或不处理，并可填写说明。待验证状态应关联“修复版本”；用户可确认通过后关闭，也可反馈仍存在并退回处理中。

### 6.7 底部导航建议

客户端首版使用三个主要入口：

| 入口 | 内容 |
| --- | --- |
| 应用 | 当前用户可测试的应用列表 |
| 反馈 | 我的 Bug、待我验证的 Bug、处理进展 |
| 我的 | 姓名、手机号脱敏展示、所属测试组、退出登录和使用帮助 |

“提交 Bug”是应用上下文中的操作，应放在应用详情内，不需要单独占用全局悬浮按钮。

## 7. Web 管理后台功能需求

### 7.1 管理员登录

- 管理员账号不得与普通用户权限混用。
- 支持手机号/账号加密码登录。
- 公网环境下限制连续失败尝试，重要操作记录管理员身份和时间。
- 首版只有一个管理员角色；如果未来多人分别负责用户、应用和 Bug，再拆分权限。

### 7.2 用户管理

- 新建用户：姓名、手机号、初始密码、测试组。
- 手机号全局唯一，重复时阻止创建。
- 编辑姓名、手机号和测试组。
- 重置密码、禁用和启用账号。
- 用户不建议物理删除，以便保留历史下载和 Bug 记录；离职或停用使用“禁用”。
- 查看用户所属测试组、可见应用、下载记录和提交的 Bug。
- 100 人以内首版支持逐个创建；批量导入可以放到 P1。

### 7.3 测试组管理

- 创建、编辑、停用测试组。
- 添加和移除组内用户。
- 给测试组分配或取消应用。
- 查看该组包含的用户、可见应用、下载人数和 Bug 数量。
- 停用测试组后，组本身不再授予应用权限，但不删除历史记录。
- 当用户属于多个组时，可见范围取各组授权应用的并集。

### 7.4 应用管理

- 创建应用并维护名称、Logo、简介、应用截图和状态。
- 应用截图支持排序、替换和删除。
- 设置应用可见测试组。
- 上传 APK 后自动读取包名、版本名称、版本代码、文件大小和最低 Android 版本等基础信息。
- 发布、更新、停止下载和下架应用。
- 下架后用户不再看到和下载，但不会卸载员工手机中已安装的应用。
- 显示应用历史版本、每个版本下载人数和 Bug 数量。

### 7.5 APK 与版本管理

- 管理员上传已构建的 APK，并填写当前版本更新内容。
- 新版本必须与原应用包名一致，版本代码必须递增。
- 平台保存 APK 文件摘要，避免上传过程中文件损坏或文件被无痕替换。
- 已发布版本的 APK 不允许直接覆盖；修改后必须上传为新版本。
- 首版只支持单个 APK 文件，不支持 split APK、APKS 或 AAB 直接安装。
- 同一时间只设置一个当前发布版本，客户端默认下载该版本。
- 可以停止当前版本下载，但保留版本、Bug 和下载历史。

#### APK 签名要求

Android 要求可安装 APK 必须经过签名。平台可以不提供签名服务，也不保存签名私钥，但必须执行以下规则：

- 拒绝无法安装的未签名 APK。
- 记录每个 APK 的签名证书摘要。
- 同一应用后续版本必须使用相同签名，否则 Android 无法正常覆盖更新。
- 如果当前研发流程“暂时没有正式签名”，首版可以使用稳定保存的内部测试签名，但不能每次生成不同签名；正式化前需要确定签名私钥的负责人和备份方式。

首版不接入恶意代码扫描，但文件类型、包结构、签名、包名、版本和哈希校验仍属于发布必需检查。

### 7.6 Bug 管理

- 按应用、版本、状态、测试组、用户和时间筛选 Bug。
- 查看标题、描述、截图、设备型号、Android 版本和提交人。
- 修改状态、填写管理员回复、处理结论和修复版本。
- 标记重复问题并关联原 Bug。
- 将含敏感信息的 Bug 设置为受限可见。
- 查看完整状态变化和回复时间线。
- 不能物理删除已处理 Bug；确需隐藏时保留后台记录。

### 7.7 下载记录

- 记录用户、手机号或用户 ID、测试组、应用、版本、下载开始时间和下载完成时间。
- 支持按用户、应用、版本、测试组和日期查询。
- 同一用户重复下载应分别保留事件，同时提供去重后的下载人数。
- 明确区分“发起下载”和“完成下载”。
- 不把下载完成表述为安装成功。
- 首版支持页面查询；CSV 导出可根据实际使用需要放到 P1。

### 7.8 管理后台首页

后台首页保持简单，展示：

- 用户总数、启用用户数、测试组数量、上架应用数量。
- 最近上传或更新的应用。
- 待处理 Bug 数量、处理中 Bug 数量和待验证 Bug 数量。
- 最近下载记录和最近管理员操作。

## 8. 服务端与文件存储需求

- 用户认证、登录态管理、账号禁用和权限校验。
- 用户、测试组、应用可见范围的服务端强制校验，不能只在客户端隐藏。
- APK、Logo、应用截图和 Bug 截图的受控存储。
- APK 下载地址应有登录鉴权或短时有效期，不能形成永久公开链接。
- Bug 截图也必须校验访问人是否有权限，不能使用可枚举的公开地址。
- 支持 APK 和图片上传进度、失败重试及文件完整性校验。
- 记录下载事件和管理员关键操作。
- 定期备份数据库及附件索引，保证恢复后 APK、版本、Bug 和截图仍能正确对应。

公网部署至少需要 HTTPS、可靠域名、数据库备份、管理员密码保护、登录限流和服务异常监控。即使用户少，也不能因“内部使用”而将 APK 或 Bug 截图公开暴露在互联网上。

## 9. 核心业务流程

### 9.1 创建内测用户

1. 管理员创建用户并绑定手机号。
2. 设置初始密码并分配测试组。
3. 将登录信息通过公司内部渠道交给员工。
4. 员工首次登录；是否强制修改初始密码待确认，建议要求修改。

### 9.2 发布首个应用版本

1. 管理员创建应用，上传 Logo、简介和应用截图。
2. 上传已签名 APK。
3. 平台解析并校验包名、版本、签名和文件摘要。
4. 管理员填写版本更新内容，选择可见测试组。
5. 管理员确认发布。
6. 目标组用户在客户端看到应用并下载；其他用户无法获得详情和下载地址。

### 9.3 更新应用

1. 管理员进入原应用并上传新 APK。
2. 平台确认包名和签名一致、版本代码递增。
3. 管理员填写更新内容并发布。
4. 客户端下次刷新时展示新版本和“更新”按钮，不发送强制或推送提醒。
5. 新提交的 Bug 自动关联新版本，历史 Bug 仍保留原版本。

### 9.4 提交与处理 Bug

1. 用户从应用详情点击“反馈 Bug”。
2. 客户端带入应用、版本、用户和设备信息。
3. 用户填写标题和说明，从相册选择系统截图后提交。
4. 管理员在后台查看并设为处理中，填写回复。
5. 修复版本发布后，管理员将 Bug 设为待验证并关联修复版本。
6. 用户验证通过后关闭；若仍存在则退回处理中。

## 10. 业务规则

1. 手机号是用户的唯一绑定标识，不允许重复。
2. 只有启用状态的账号可以登录、查看应用和下载。
3. 用户只能查看其所属测试组被授权的应用。
4. 应用详情、APK 下载和 Bug 内容均须由服务端校验权限。
5. 应用以 Android 包名作为稳定标识，同一包名不能创建多个应用。
6. 同一应用的新版本必须保持包名和签名一致，版本代码递增。
7. 已发布 APK 不允许原地替换。
8. 每个 Bug 必须关联应用和版本，并保留状态变化历史。
9. 用户只能修改尚未被管理员处理的 Bug 文本；开始处理后采用追加回复，避免历史内容被改写。
10. 下载完成只代表 APK 文件已下载到客户端，不代表安装成功。
11. 应用下架不会自动卸载员工手机上的应用。
12. 被禁用用户的历史 Bug 和下载记录继续保留。

## 11. 非功能需求

### 11.1 性能与容量

- 按 100 个以内启用用户和低并发场景设计，不要求首版配置复杂 CDN。
- 常规登录、列表、详情和 Bug 查询在正常公网条件下应快速响应。
- APK 下载不应占用业务接口进程长期传输资源，文件存储需要支持稳定下载和续传能力。
- Logo、应用截图和 Bug 截图生成合适尺寸的预览图，避免列表加载原始大图。

### 11.2 安全

- 全站 HTTPS。
- 密码使用可靠的不可逆算法加盐保存，不能明文存储。
- 登录失败限流，管理员账号建议使用更强密码并支持后续增加双因素认证。
- 客户端登录令牌存放在 Android 安全存储中。
- APK 和截图均不提供永久公开地址。
- 上传文件检查扩展名、实际文件类型、文件大小和完整性。
- 管理员操作、账号禁用、应用发布和下架需要留痕。

### 11.3 可用性与可恢复性

- 下载、图片上传和 Bug 提交均应显示明确进度和失败原因。
- Bug 文本在上传失败、应用切到后台或网络中断后尽量保留草稿。
- 服务端和数据库定期备份，并至少完成一次恢复验证。
- 客户端覆盖加载中、空数据、无权限、网络错误、账号失效和文件下载失败状态。

### 11.4 兼容性与无障碍

- Android 最低支持版本需要在开发前根据员工设备盘点确定。
- 适配主流屏幕尺寸、系统深色模式、系统字体放大、手势导航和三键导航。
- 表单不能被软键盘遮挡，输入失败后保留已填写内容。
- 图标按钮有文字或无障碍名称，状态不能只依赖颜色表达。

## 13. MVP 范围

### 13.1 首版必须包含

- 管理员创建手机号账号、重置密码、禁用账号。
- 测试组及用户成员管理。
- 应用对测试组的可见范围配置。
- 应用资料、Logo、展示截图管理。
- 单 APK 上传、基础解析、版本/包名/签名/哈希校验。
- 应用发布、更新和下架。
- Android 客户端登录、应用列表、详情、下载和系统安装引导。
- 版本更新内容展示，不做推送和强制升级。
- Bug 创建、截图上传、列表、详情、管理员回复和状态流转。
- 下载开始/完成记录和基础查询。
- 公网访问安全、备份和基础监控。

### 13.2 后续可增加

- 手机短信验证码登录和自助找回密码。
- 用户批量导入、下载记录导出。
- 从系统截图通知或相册直接“分享到内测平台”。
- 截图标注、打码、裁剪和圈选。
- Bug 指派、优先级、标签、重复问题自动提示。
- 消息推送和新版本提醒。
- 多管理员角色和审批流程。
- CI/CD 自动上传 API。
- 灰度发布、强制升级、MDM 或静默安装。

### 13.3 明确不做

- iOS 和桌面端应用分发。
- 员工自助注册及外部人员账号。
- 公开应用市场、评论评分、支付和广告。
- AAB、APKS、split APK 和差分更新。
- 在线构建 APK 或托管业务应用签名私钥。
- 静默安装、远程卸载、设备管控和强制升级。
- 首版恶意代码扫描系统集成。
- 高权限的跨应用自动截图或悬浮测试工具。

## 14. MVP 验收场景

1. 管理员创建手机号账号并分配测试组后，用户能够登录；账号禁用后无法继续访问。
2. 同一应用授权给 A 组后，A 组用户可以看到，B 组用户无法查看详情或获取下载地址。
3. 管理员上传合法 APK 后，平台展示包名、版本、大小和签名；未签名、包名不一致、签名不一致或版本未递增时拒绝发布。
4. 用户能够查看 Logo、名称、版本、应用截图和更新内容，完成 APK 下载并进入 Android 系统安装界面。
5. 下载开始和完成分别生成记录，后台可以按用户、应用、版本和时间查询。
6. 用户可以提交包含标题、说明和多张截图的 Bug，失败重试不会丢失已填写文字。
7. 管理员可以回复 Bug，并在待处理、处理中、待验证和已关闭之间正确流转。
8. 用户能够看到自己的 Bug、管理员回复和状态时间线；同组用户只能看到允许公开的内容，不能看到提交者手机号。
9. 新版本发布后，客户端刷新即可展示“更新”和新版本说明，不主动推送或强制安装。
10. 应用下架后客户端不再显示下载入口，旧下载地址失效，但历史 Bug 和下载记录仍保留。

## 15. 仍需确认的少量问题

以下问题不影响当前需求框架，但会影响后续原型和技术方案：

1. 登录最终采用“手机号 + 密码”，还是“手机号 + 短信验证码”？
2. 是否要求用户首次登录强制修改管理员设置的初始密码？
3. 应用 Bug 是否默认对同一应用的全部测试用户可见，还是只允许用户看自己的 Bug？
4. Bug 截图是否允许全部同组用户查看，还是默认只对提交人和管理员可见？
5. 希望支持的最低 Android 版本是什么，或能否先收集内测员工的 Android 版本分布？
6. 第一个“内测平台客户端”本身如何交付给员工：公网下载页、二维码、公司聊天工具链接，还是线下预装？
7. 是否已有公司域名、HTTPS 证书和可用的公网服务器/对象存储？

## 16. 建议下一步

1. 确认第 15 节的登录、Bug 可见性和客户端首次分发方式。
2. 选一个真实 APK，核对包名、签名、版本和更新流程。
3. 基于本文制作客户端与后台的低保真页面流程图。
4. 定义数据库对象、API 边界和技术方案。
5. 需求评审通过后，再开始搭建项目和编写代码。
