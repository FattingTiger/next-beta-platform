# NEXT 内测平台：Google Stitch 提示词与项目框架

## 一、推荐的使用方式

1. 在 Stitch 新建项目，把本目录的 `DESIGN.md` 作为设计规则导入或贴到项目画布。
2. 上传 `brand/NEXT-brand-direction-board.png` 作为品牌方向参考；Android 项目再上传 `brand/NEXT-android-icon-concept.png`。
3. Web 管理后台与 Android 客户端分成两个设计分支，共用同一份 Design System。
4. 先生成下面列出的 3 个重点页面，确认视觉方向后再补其余页面。
5. 每次迭代只改一个明确问题，例如“降低卡片阴影并提高表格密度”，不要在一条指令里同时改布局、颜色、文案和交互。
6. 最终将页面串成原型，走完“管理员发布应用”和“员工下载并反馈 Bug”两条主流程。

## 二、项目框架需求

### 2.1 产品定位

NEXT 内测平台是一套部署在公网、服务于不超过 100 名公司员工的 Android 内测应用分发平台。员工使用自己的普通 Android 手机，无定制 ROM。管理员通过 Web 后台管理测试应用；员工通过 Android 客户端下载安装获准测试的应用并反馈 Bug。

### 2.2 角色与权限

| 角色 | 权限 |
|---|---|
| 管理员 | 创建和管理用户、绑定手机号、创建测试组、上传与发布 APK、上传应用 Logo/截图、设置可见测试组、查看下载记录、处理 Bug、查看审计日志、归档或永久删除条目 |
| 内测员工 | 手机号与密码登录、查看所属测试组可见应用、查看版本和截图、下载 APK、查看自己或相关应用的 Bug、上传截图并提交反馈、跟踪处理状态 |

不提供外包/合作方账号，不提供普通用户上传 APK，不需要双人审核。

### 2.3 当前范围

- 公网访问，小规模内测，不考虑海外、专网、超大 APK 或极端弱网。
- 不支持静默安装、强制升级、远程卸载。
- 不设计灰度、测试/生产多通道或复杂审批流。
- 不设计恶意代码扫描平台，但后台需要显示 APK 基本解析与签名校验结果。
- 记录下载请求和客户端校验完成；不能把“下载完成”描述为“安装成功”。
- Android Bug 反馈支持选择/拍摄截图、标题、问题说明、复现步骤，最多 5 张截图，并能查看处理进度与评论。

### 2.4 信息架构

#### Web 管理后台

1. **发布概览**：正在内测应用、已发布版本、未关闭 Bug、近 7 天下载请求/完成、正在测试的应用卡片、最近 Bug。
2. **应用与版本**：搜索和筛选、应用列表、批量管理、新建应用、应用详情、编辑资料、上传 Logo/截图、上传 APK、发布/归档/恢复/永久删除。
3. **测试组**：测试组、成员数、关联应用、创建/编辑、批量停用/恢复/永久删除。
4. **Bug 反馈**：状态、应用、版本、反馈人、截图、处理记录、评论、批量删除/恢复/永久删除。
5. **用户管理**：手机号、姓名、角色、所属组、状态、创建/编辑、重置密码、批量停用/恢复/永久删除。
6. **下载记录**：用户、应用、版本、发起时间、完成时间、状态、设备摘要和筛选。
7. **审计日志**：谁、何时、对什么对象、执行了什么操作、结果；页面须解释其用途。
8. **登录/重新验证**：管理员手机号与密码；敏感操作要求输入当前管理员密码。

#### Android 客户端

1. **登录与首次改密**。
2. **应用首页**：只显示当前用户所属测试组可见且已发布的应用。
3. **应用详情**：Logo、名称、版本、更新内容、截图、安装包大小、发布时间、下载/校验/安装入口、Bug 摘要。
4. **提交 Bug**：当前应用和版本不可误选，标题、问题说明、复现步骤、截图选择/拍摄、草稿保存、提交状态。
5. **反馈列表与详情**：筛选“我的反馈/当前应用”、状态、图片、评论、处理时间线、待验证操作。
6. **我的**：账号、手机号、测试组、退出登录。

### 2.5 核心数据对象

| 对象 | 关键字段 |
|---|---|
| User | 姓名、手机号、角色、状态、测试组、首次改密状态 |
| TestGroup | 名称、说明、成员、可见应用、启用状态 |
| App | 名称、包名、简介、说明、Logo、截图、状态、可见测试组 |
| AppVersion | versionName、versionCode、APK、包大小、更新说明、发布时间、签名摘要、状态 |
| Bug | 编号、应用、版本、反馈人、标题、说明、复现步骤、状态、截图、评论、状态流转 |
| DownloadRecord | 用户、应用、版本、发起时间、完成时间、状态、文件校验结果 |
| AuditLog | 操作人、动作、对象、时间、结果、必要的变更摘要 |

状态建议：

- 应用：草稿 / 已发布 / 已归档
- Bug：待处理 / 处理中 / 待验证 / 已关闭
- 下载：已发起 / 下载中 / 已完成 / 失败 / 已取消
- 用户和测试组：启用 / 停用

### 2.6 关键流程

**管理员发布应用**：新建应用 → 上传 Logo 与截图 → 上传 APK → 查看解析/签名结果 → 填写更新说明 → 选择测试组 → 发布 → 发布概览出现应用卡片。

**员工内测反馈**：登录 → 浏览可见应用 → 查看版本与更新内容 → 下载并校验 APK → 跳转系统安装 → 测试应用 → 回到 NEXT 提交截图与说明 → 查看处理进度 → 在待验证状态确认解决或退回。

**批量管理**：点击“批量管理” → 每行出现复选框 → 选择条目 → 批量归档/停用或恢复 → 对已归档/停用条目可选择永久删除 → 展示影响范围 → 输入当前管理员密码 → 执行并显示逐项结果。

## 三、可直接粘贴给 Stitch 的全局项目提示词

```text
请为“NEXT 内测平台”建立一套统一的 Web 管理后台和 Android 客户端设计系统，并先完成重点页面。

产品是一套公司内部 Android 应用内测分发平台，部署在公网，服务不超过 100 名员工。员工使用自己的普通 Android 手机。管理员通过 Web 后台上传和发布 APK、维护应用 Logo/截图、创建用户和测试组、控制每个应用的可见范围、查看下载记录并处理 Bug。员工在 Android 客户端用手机号和密码登录，只能看到所属测试组获准测试的应用，能够查看版本、更新说明和截图，下载 APK，并上传最多 5 张截图反馈 Bug，跟踪待处理、处理中、待验证、已关闭状态。

品牌名称为“NEXT 内测平台”，英文短名“NEXT Beta”。使用上传的 NEXT 品牌方案作为视觉参考：钴蓝、墨绿色、青绿色和暖白色；核心是由应用卡片构成的 N 形图标和小型验证标记。界面应可信、清楚、安静、精确，有现代卡片层级和克制的拟物质感。拟物质感主要用于品牌、重点摘要和少量状态反馈；正文、表格与表单必须保持高可读性。可以借鉴 Apple Developer 的信息层级和 App Store 的内容编排，但不要复制 iOS 控件。

避免常见紫色渐变 SaaS 模板、霓虹光晕、无意义折线图、图库照片、过度玻璃、所有内容都装进卡片、危险操作只用无文字图标等问题。使用开源中文字体 Noto Sans SC 或 Source Han Sans SC，英文与数字可用 Inter。满足 WCAG AA，状态不能只靠颜色表达。

Web 使用桌面优先的响应式布局，1440 px 主画板并适配 1280/1024 px；左侧导航包括发布概览、应用与版本、测试组、Bug 反馈、用户管理、下载记录、审计日志。Android 使用 Material Design 3 可实现的模式，412×915 dp 主画板并适配 360×800 dp，底部导航为应用、反馈、我的，触控目标至少 48 dp。

必须设计真实业务状态：加载、空数据、失败、无权限、选中、批量操作、上传中、上传失败、危险操作确认。下载统计统一称为“下载请求”和“下载完成”，明确下载完成仅表示文件校验通过，不代表安装成功。永久删除前必须展示影响范围并输入当前管理员密码确认。

先建立可复用的颜色、字体、间距、圆角、阴影、按钮、状态标签、表格、应用卡片、截图画廊、筛选条、批量操作条、空状态、错误状态和确认弹窗组件。随后分别生成 Web 和 Android 的重点页面，保持同一品牌但遵循各自平台习惯。
```

## 四、Web 管理后台重点三页提示词

### 4.1 发布概览

```text
基于 NEXT 项目设计系统，设计 1440×1024 的 Web“发布概览”页面。

页面顶部是“发布概览”和说明“查看当前内测应用、版本发布与反馈处理情况”。第一块是宽幅深墨绿色摘要卡，左侧标题使用具体事实“1 个应用正在内测”，下面写“当前有 1 个已发布版本面向测试用户开放。近 7 天发起 4 次下载，完成 4 次；下载完成仅代表文件校验通过，不代表安装成功。”右侧四个紧凑事实块：正在内测应用 1、已发布版本 1、未关闭 Bug 0、下载完成率 100%。不要使用“发布面保持清晰”“等待闭环”等抽象文案。

摘要卡下方展示三个辅助指标卡：活跃用户、近 7 天下载请求、近 7 天下载完成，每个都带清楚的解释提示。主要内容区使用类似开发者中心的应用卡片网格展示“正在测试的应用”：Logo、名称、包名、当前版本、测试组、未关闭 Bug、最近更新和“查看详情”。右侧或下方安排“最近更新的 Bug”列表。

视觉要有现代卡片层级、适度留白、清晰数字和克制玻璃/拟物细节。不要加入无数据依据的增长曲线。补充加载、无正在测试应用和请求失败状态。
```

### 4.2 应用与版本

```text
基于 NEXT 项目设计系统，设计 1440×1024 的 Web“应用与版本”管理页。

顶部有标题、说明、新建应用主按钮和刷新。筛选区包括应用名称/包名搜索、状态、测试组和清除。主体是适合桌面管理的高可读表格：应用 Logo 与名称/包名、状态、当前版本、可见测试组、最近更新、操作。

默认模式每行提供有文字的“详情”和“编辑”，危险或生命周期操作放在清楚的更多操作菜单中。点击“批量管理”后，表头和每行首列出现复选框，顶部或底部出现吸附的批量操作条，显示已选数量、全选本页、归档、恢复、永久删除和退出管理。永久删除只允许处理已归档条目，点击后弹窗列出条目与影响，要求输入当前管理员密码，并明确“不可恢复”。

同一设计中给出应用详情抽屉或独立详情页的关键区域：应用资料、展示截图、版本历史、测试组范围、APK 解析和签名信息、上传新版本。补充空列表、上传中、上传失败、部分批量失败与无权限状态。不要让删除操作只表现为垃圾桶小图标。
```

### 4.3 Bug 反馈

```text
基于 NEXT 项目设计系统，设计 1440×1024 的 Web“Bug 反馈”页面。

页面以处理工作为核心。顶部显示未关闭数量与状态分布，筛选包括关键词、应用、版本、反馈人和状态。主体列表显示 Bug 编号、标题、应用/版本、反馈人、截图数量、状态、更新时间。状态为待处理、处理中、待验证、已关闭，并同时使用文字和图形区分。

详情使用宽抽屉或双栏布局：左侧为标题、说明、复现步骤与截图证据；右侧为当前状态、反馈人/设备摘要、状态时间线、管理员评论和状态操作。批量管理模式支持选择后删除、恢复和对已删除反馈执行密码确认的永久删除。设计截图放大、评论提交中、状态冲突、图片加载失败和空状态。
```

## 五、Android 客户端重点三页提示词

### 5.1 应用首页

```text
基于 NEXT 项目设计系统，设计 Android 412×915 dp 的“应用”首页，使用 Material Design 3 可实现的交互。

顶部显示 NEXT Beta 品牌、小型账号入口和欢迎语“这些应用正在等待你的测试”。主体只展示当前用户有权限且已发布的应用。使用信息丰富但不过度装饰的应用卡片：Logo、应用名、当前版本、简短介绍、更新时间、测试状态和“查看”入口。第一张重点卡可展示一张应用截图，但不要让所有卡片变成海报。

底部导航为应用、反馈、我的。设计正常、首次没有应用、加载骨架、网络错误和离线状态。不要直接在首页提供不明确的安装按钮；用户先进入详情确认版本信息。
```

### 5.2 应用详情与下载

```text
基于 NEXT 项目设计系统，设计 Android 412×915 dp 的应用详情页。

顶部显示返回、应用 Logo、名称、版本号、安装包大小、更新时间与简介。中段是可横向浏览的真实应用截图，随后是“本次更新”和完整说明。底部使用清晰的吸附操作区，主按钮根据状态展示：下载、等待下载、下载中 46%、正在校验、去安装、重试。旁边提供“反馈 Bug”次要入口。

页面还要显示该应用的 Bug 状态摘要和“查看反馈”。明确提示 Android 会跳转系统安装界面，平台不会静默安装；下载完成只表示 APK 文件校验通过。设计下载权限被拒、存储不足、校验失败、版本已更新和系统阻止未知来源安装等状态。
```

### 5.3 提交 Bug 与处理跟踪

```text
基于 NEXT 项目设计系统，设计 Android 412×915 dp 的“提交 Bug”页面，并在同一画布给出提交后的 Bug 详情状态。

提交页顶部固定显示当前应用和版本，不能让用户误报到其他版本。字段包括 Bug 标题、问题说明、复现步骤；截图区支持从相册选择或拍摄，最多 5 张，显示缩略图、上传顺序、删除和上传失败重试。表单自动保存草稿。主按钮为“提交反馈”，提交中不可重复点击，失败后保留所有内容。

提交后的详情页显示 Bug 编号、状态标签、截图、原始描述、评论和从待处理→处理中→待验证→已关闭的时间线。待验证时给报告人“确认已解决”和“问题仍存在”两个清楚操作。设计无截图、图片加载失败、离线草稿、提交成功和状态已被管理员更新的情况。
```

## 六、补充页面的短提示词

- **测试组**：使用成员和关联应用双摘要；编辑时分开“组资料、成员、可见应用”；支持批量停用/恢复/永久删除。
- **用户管理**：手机号是账号标识；表格展示姓名、手机号、角色、测试组、状态；禁止当前管理员永久删除自己。
- **下载记录**：强调这是下载事件而非安装统计；支持按用户、应用、版本、状态和时间筛选。
- **审计日志**：页首解释“记录管理员的关键操作，用于追踪谁在何时修改了什么”；列表按时间倒序并能查看变更摘要。
- **登录页**：使用 NEXT 拟物品牌图标作为唯一主视觉；表单只含手机号、密码和登录，不增加注册、社交登录或营销模块。

## 八、交付验收清单

- Web 与 Android 是否一眼能看出属于同一个 NEXT 产品。
- 首页是否优先展示真实任务，而非装饰性大数据。
- 应用、版本、测试组、Bug、用户之间的关系是否清楚。
- 批量管理是否只在进入管理模式后显示复选框，并能退出。
- 归档/停用与永久删除是否被清楚区分。
- 永久删除是否要求当前管理员密码并显示不可恢复影响。
- 下载请求、下载完成、安装成功三个概念是否没有混淆。
- Android 是否遵循系统安装和系统返回习惯。
- 截图证据、错误状态、空状态、加载状态、长中文和 360 dp/1024 px 窄屏是否都有设计。
- 所有重要操作是否有文字标签、足够对比度和可达的键盘/触控目标。
