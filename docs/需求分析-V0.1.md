# 公司内部 Android 应用分发平台需求分析 V0.1

> 状态：讨论稿  
> 日期：2026-08-28  
> 本阶段仅分析产品需求与边界，不涉及技术选型和代码实现。

## 1. 产品定位

建设一个仅面向公司内部人员的 Android 应用分发平台。员工通过 Android 客户端查找、下载、安装和更新有权限使用的内部应用；应用负责人、安全人员和平台管理员通过管理后台完成应用上传、审核、发布、分发范围控制、版本管理和审计。

平台需要解决四类问题：

1. 内部 APK 有统一、可信的发布入口，避免通过聊天工具和网盘零散传播。
2. 不同部门、项目组和人员只能看到并安装其被授权的应用。
3. 应用版本、签名、发布记录和下载行为可追踪、可审计。
4. 员工能够及时收到更新，关键版本能够按公司策略推进升级。

## 2. 当前分析假设

- 首期只支持 Android 手机和平板，不包含 iOS、Windows 和 macOS。
- 平台由三部分组成：Android 员工端、Web 管理后台、平台服务端。
- 分发对象以公司员工为主，也可能包含外包人员、测试人员和特定合作方。
- 公司已有或计划接入统一身份认证；具体是 LDAP、AD、OIDC、SAML 还是企业微信/飞书待确认。
- APK 由各业务研发团队完成构建和签名，平台原则上不托管业务应用的签名私钥，只验证签名和版本一致性。
- 首版优先兼容普通、未纳管设备的安装流程，并为后续 MDM/Device Owner 模式预留能力。

## 3. 用户角色

| 角色 | 主要职责与权限 |
| --- | --- |
| 普通员工 | 浏览被授权的应用，下载、安装、更新，查看版本说明和通知 |
| 应用负责人 | 创建应用、维护应用资料、上传版本、指定测试或发布范围、查看本应用数据 |
| 发布审核人 | 审核应用信息、版本变更、权限变化和发布范围，批准或驳回发布 |
| 安全审核人 | 查看 APK 检测结果、签名和敏感权限变化，处理风险版本 |
| 平台运营人员 | 管理分类、推荐位、公告、应用上下架和用户反馈 |
| 平台管理员 | 管理组织、角色、全局策略、系统配置和审计日志 |
| 审计人员 | 只读查看发布、权限、下载、安装结果和管理员操作记录 |

首版可将“发布审核人”和“安全审核人”合并，避免流程过重；平台管理员不应默认拥有业务 APK 的签名私钥。

## 4. 关键产品决策：设备分发模式

### 4.1 普通设备模式

适用于员工自有设备或未被公司 MDM 纳管的设备。

- 用户首次安装内部应用前，需要在 Android 系统设置中允许本平台客户端“安装未知应用”。
- 新应用安装通常需要用户在系统安装界面确认。
- 平台可以下载 APK、发起系统安装、展示安装状态，但不能承诺所有设备均可无感静默安装。
- 强制升级只能通过平台入口限制、应用自身配合或后端业务接口限制来推进，无法仅靠普通分发客户端绝对保证。

### 4.2 受管设备模式

适用于公司配发且通过 Android Enterprise/MDM 纳管的设备。

- 当平台或其配套的设备策略控制器具备 Device Owner/Profile Owner 等受管能力时，可实现更强的静默安装、批量推送、安装策略和合规控制。
- 需要额外建设或对接 MDM、设备注册、设备策略和合规状态同步，不建议在尚无设备管理基础时直接纳入最小可用版本。

### 4.3 定制系统模式

通过系统预装、系统签名或设备厂商能力获得更高安装权限，适合专用终端。该模式对 ROM、设备型号和供应链依赖较强，不作为通用员工手机方案。

**首版建议：** 采用“普通设备手动确认安装”，同时在数据模型和发布策略中预留受管设备字段。如果公司现有设备已全部被 MDM 纳管，则应改为优先对接 MDM。

## 5. 核心业务流程

### 5.1 应用首次发布

1. 应用负责人创建应用条目并填写名称、图标、简介、负责人、隐私说明和支持方式。
2. 上传已签名 APK，平台自动解析包名、版本号、版本代码、SDK 要求、CPU 架构、签名证书摘要、文件摘要和权限列表。
3. 平台执行文件完整性、恶意代码和策略检查，并对比历史版本的签名、权限及包名变化。
4. 负责人填写更新说明，选择可见范围、发布策略和发布时间，提交审核。
5. 审核人查看检测结果及变更差异，批准或驳回。
6. 通过后发布；目标员工可在客户端看到应用并下载安装。

### 5.2 版本更新

1. 上传新版本并校验包名相同、签名证书一致、`versionCode` 高于已发布版本。
2. 展示新增/删除权限、SDK、架构、文件大小和签名差异。
3. 配置普通更新、推荐更新、限期更新或强制更新策略。
4. 审核后按目标范围发布，可选择立即发布、定时发布或分批发布。
5. 客户端检测本机版本并提示更新，记录下载及安装结果。

### 5.3 下架和回滚

- 下架后，新用户不可下载，但已安装应用不会被普通客户端自动卸载。
- 紧急版本可以停止分发并撤销下载链接。
- 回滚本质上应发布一个 `versionCode` 更高、业务内容回退的新 APK；不能简单把较低版本覆盖到设备上。
- 如需远程卸载或禁用，依赖受管设备能力或业务应用自身的服务端开关。

## 6. 功能需求

### 6.1 Android 员工端

#### 登录与身份

- 接入公司统一登录，支持登录态续期、退出登录和账号禁用。
- 获取员工所属部门、角色、用户组和应用授权范围。
- 可选采集设备标识、系统版本、机型和客户端版本；采集范围需经过隐私与合规确认。
- 对离职、账号冻结或授权撤销及时生效。

#### 应用发现

- 首页展示推荐、最近更新、必装应用和公告。
- 支持分类、搜索、应用列表和应用详情。
- 应用详情包含图标、名称、版本、大小、更新时间、简介、截图、更新说明、负责人、支持方式和权限说明。
- 仅展示当前用户有权访问且与设备基本兼容的应用。

#### 下载、安装与更新

- 展示未安装、可打开、可更新、下载中、等待安装、安装成功和安装失败等状态。
- 支持断点续传、失败重试、网络切换提示和下载进度。
- 下载前检查存储空间、网络策略和设备兼容性。
- 首次使用时引导用户授予“安装未知应用”权限。
- 调起 Android 系统安装流程，处理用户取消、签名冲突、空间不足、APK 无效和设备不兼容等结果。
- 支持检查更新、更新提醒和必装/限期更新提示。
- 平台客户端自身必须具备可靠的自更新或预置更新通道。

#### 通知与帮助

- 接收新应用、版本更新、强制升级、下架和安全公告。
- 提供安装权限开启指引、常见错误说明和问题反馈入口。
- 通知需要支持已读状态和按应用/类型控制，强制安全通知除外。

### 6.2 Web 管理后台

#### 应用管理

- 创建、编辑、归档应用，维护图标、截图、分类、标签、负责人和支持方式。
- 一个应用以 Android 包名作为稳定技术标识；同一包名不得创建重复应用。
- 支持应用草稿、审核中、待发布、已发布、已下架和已归档等状态。
- 应用负责人只能管理自己负责的应用，跨应用操作需更高权限。

#### 版本管理

- 上传 APK 并自动解析元数据。
- 校验文件 SHA-256、包名、签名证书、版本代码、最低系统版本、目标系统版本、CPU 架构和权限。
- 展示与上一版本的差异，重点标记签名变化和新增敏感权限。
- 支持发布说明、发布时间、下载网络策略和目标范围。
- 支持普通、推荐、限期和强制更新策略。
- 保留历史版本和发布记录；是否允许下载历史版本应由权限控制。
- 支持单 APK；若业务应用采用 split APK/APKS 等交付形式，需要单独确定首版是否支持。

#### 发布与审核

- 支持提交、批准、驳回、撤回、定时发布、停止分发和下架。
- 审核页集中展示 APK 检测结果、权限变化、签名信息和目标人群。
- 高风险变更可要求二次审核，例如签名变化、敏感权限新增或分发范围扩大。
- 紧急发布需要单独权限、原因填写和完整审计。

#### 分发范围

- 可按全员、部门、用户组、个人、设备组和测试组授权。
- 支持包含与排除规则，冲突时以更严格的规则优先。
- 支持测试、灰度和正式三个发布通道；首版至少需要测试和正式通道。
- 授权撤销后应立即阻止新的详情访问和下载链接获取。

#### 组织、权限与审计

- 同步或维护组织、人员、用户组、角色和账号状态。
- 使用基于角色的后台权限控制，并支持按应用限定管理范围。
- 记录登录、上传、审核、发布、下架、授权变更和系统配置变更。
- 审计日志不可由普通管理员篡改，并支持按人员、应用、时间和操作类型检索导出。

#### 数据统计

- 应用浏览量、下载次数、下载用户数、安装成功/失败数量、版本分布和更新完成率。
- 按部门、用户组、版本和时间筛选。
- 明确区分“下载成功”和“安装成功”；未受管设备上的安装结果可能因系统及厂商限制不完整，需要标注数据口径。

### 6.3 平台服务能力

- 身份认证、组织同步和访问令牌管理。
- 应用元数据、版本、发布通道和授权策略管理。
- APK 对象存储、加密传输、短时效下载地址和断点续传。
- APK 元数据解析、签名校验、哈希校验、恶意文件扫描和权限差异分析。
- 通知、定时发布、灰度策略和状态回调。
- 操作审计、异常告警、数据备份和恢复。

## 7. 核心业务规则

1. 包名唯一：一个包名只能归属一个平台应用。
2. 签名连续：同一应用的新版本必须与已发布版本使用一致签名；更换签名走特殊迁移和高风险审批。
3. 版本递增：更新版本的 `versionCode` 必须高于目标通道已发布版本。
4. 先审后发：未通过审核的 APK 不得进入正式分发范围。
5. 最小可见：用户只能查询并下载明确授权的应用和版本，不能仅靠前端隐藏。
6. 下载鉴权：APK 地址必须受鉴权并有有效期，不提供长期公开链接。
7. 已发布文件不可替换：相同版本如需修改必须创建新版本，防止审计记录与实际文件不一致。
8. 下架不等于卸载：普通设备上的已安装应用不会因平台下架而自动消失。
9. 强制更新需定义责任边界：平台可以阻止旧版继续从商店获得服务，但能否禁止业务应用运行取决于业务应用或其服务端是否配合。
10. 所有发布、授权和风险处置操作均需记录操作者、时间、对象、前后值和原因。

## 8. 安全与合规要求

### APK 与供应链安全

- 计算并保存 APK 的 SHA-256，下载后再次校验。
- 校验 APK 签名证书及签名方案，阻止签名不一致的覆盖更新。
- 接入恶意代码/病毒扫描；高风险结果不得自动发布。
- 标记敏感权限及权限增量，例如短信、通话记录、联系人、定位、辅助功能和设备管理权限。
- 建议保留构建来源、代码仓库提交、流水线编号或制品来源，逐步形成可追溯的软件供应链。
- 业务应用签名私钥应由各应用团队或公司集中签名系统保管，不应随 APK 上传至分发平台。

### 平台与数据安全

- 全链路 HTTPS，服务端敏感配置和凭据使用专用密钥管理。
- 管理后台启用统一身份认证和多因素认证，关键操作可二次确认。
- 遵循最小权限原则，区分应用管理、审核、平台管理和审计角色。
- 防止 APK 链接被转发后长期有效，记录下载主体、文件版本和结果。
- 明确设备信息的采集目的、保存期限、访问人员和员工告知方式。
- 定义日志留存期限、备份周期、恢复目标和安全事件响应流程。

### 2026 年后的 Android 分发要求

- Android 正在推进开发者身份和包名注册要求。2026-09-30 起先在部分国家和参与商店执行，计划于 2027 年扩大到全球认证 Android 设备。
- 官方当前说明：组织商店分发到受管设备的企业应用可不受该验证要求约束；但若应用可能分发到非受管设备或从其他来源安装，仍建议公司完成开发者身份验证并登记包名。
- 因此，项目立项时应登记每个内部应用的签名归属和包名负责人，并把 Android Developer Console/Play Console 的组织验证与包名登记纳入合规清单。

## 9. 非功能需求建议基线

以下数值是首轮评审建议，不是已确认指标：

| 类别 | 建议基线 |
| --- | --- |
| 可用性 | 核心下载与发布服务月可用性不低于 99.9% |
| 性能 | 常规列表/详情接口在正常网络下 P95 小于 1 秒；APK 下载速度主要受存储、带宽和网络影响 |
| 并发 | 根据员工规模和集中发布时间核算，至少支持全员发布后的突发下载 |
| 容量 | APK、历史版本、截图和日志分别制定容量与保留策略 |
| 兼容性 | Android 最低版本、目标版本、主流厂商机型和 CPU 架构需由设备盘点决定 |
| 灾备 | 定义 RPO/RTO；应用元数据、权限和审计记录优先于可重新上传的制品恢复 |
| 可观测性 | 覆盖登录、上传、解析、审核、发布、鉴权、下载和通知链路，异常可告警 |
| 可维护性 | 业务配置与发布策略可在后台管理，避免依赖人工修改数据库 |

## 10. 最小可用版本（MVP）建议

### MVP 必须包含

- Android 客户端：统一登录、应用列表/分类/搜索、详情、下载、系统安装引导、更新检测、公告和基本错误提示。
- 管理后台：应用资料、APK 上传与解析、签名/版本校验、测试与正式发布、人员/部门范围、上下架、基础角色权限、审计日志。
- 平台服务：统一认证、授权校验、对象存储、短时效下载、APK 完整性校验、基础安全扫描、通知和基础统计。
- 运行保障：日志、监控、备份、关键异常告警和管理员操作审计。

### 建议后置到 P1

- 分批灰度、按设备型号/系统版本分组、限期升级、精细化报表。
- MDM/Android Enterprise 对接、静默安装、远程卸载和设备合规策略。
- 多级审批、自动化发布 API、CI/CD 流水线集成。
- 多 APK/split APK 交付、增量包、差分更新和大规模 CDN 优化。
- 用户评价、评论、推荐算法和个性化首页。

### 首版明确不做

- iOS 或桌面端应用分发。
- 应用在线开发、编译和代签名。
- 面向公网用户的商业应用市场、支付、订阅和广告。
- 在未受管普通 Android 设备上承诺静默安装或无条件远程卸载。

## 11. MVP 验收场景

1. 已授权员工登录后可找到目标应用，未授权员工无法搜索、查看详情或获取下载地址。
2. 管理员上传 APK 后，平台能够解析包名、版本、签名、SDK、架构和权限；不符合规则时禁止发布并说明原因。
3. 审核通过后，应用只对指定测试组或正式范围可见，且发布、驳回和下架均有审计记录。
4. 普通设备首次安装时，客户端能引导开启安装来源权限并调起系统安装；用户取消或安装失败时能看到可理解的提示。
5. 已安装旧版的员工能收到更新提示；签名不一致、版本不递增或设备不兼容的 APK 不进入正常更新流程。
6. 应用下架或员工授权撤销后，新的下载令牌立即失效，客户端不再展示可下载入口。
7. 平台能区分浏览、下载开始、下载完成和安装结果，并注明统计口径。
8. APK 文件、发布元数据和审计日志在备份恢复演练后保持对应关系。

## 12. 待确认问题

### 最高优先级

1. 员工手机是公司统一配发并受 MDM 管理，还是允许 BYOD/未纳管设备？两者占比如何？
2. 是否已经有 MDM、Android Enterprise、定制 ROM 或设备厂商管理平台？
3. 登录要接入哪套身份系统？组织和离职状态从哪里同步？
4. 应用规模、员工规模、设备数量，以及一次全员发布可能产生的峰值下载量是多少？
5. 平台部署在公司内网、VPN、零信任网络还是公网？员工在外网是否需要下载安装？
6. 是否要求“静默安装、强制升级、远程卸载”？如果要求，哪些设备必须实现？

### 产品与流程

7. 谁可以上传 APK，谁负责安全审核和发布批准？是否需要双人审批？
8. 应用可见范围需要支持到部门、项目组、个人、设备组中的哪些层级？
9. 是否需要测试、灰度、正式多通道，以及定时发布和分批比例？
10. 是否允许外包或合作方账号，是否需要到期自动失效？
11. 是否需要业务应用配合实现旧版本停用，还是只要求商店侧提醒？
12. 是否存在超大 APK、弱网、海外办公或专网场景？

### 安全与合规

13. 公司现有恶意代码扫描、制品库、CI/CD、密钥管理和安全审批系统有哪些？
14. APK 的签名由各业务团队保管，还是公司有统一签名服务？
15. 设备信息、下载记录和安装结果允许采集到什么粒度，保存多久？
16. 是否有等保、数据出境、审计留存或行业监管要求？

## 13. 建议的下一步

1. 先回答第 12 节的六个最高优先级问题，确定设备模式、身份体系、部署边界和规模。
2. 选取 2～3 个真实内部应用，走一遍上传、审核、定向发布、安装、更新、下架流程，校准需求。
3. 形成 MVP 功能清单、角色权限矩阵、发布状态机和关键页面流程图。
4. 在需求边界确认后再进入技术方案，包括服务拆分、存储、下载链路、Android 安装实现和 MDM 对接方式。
